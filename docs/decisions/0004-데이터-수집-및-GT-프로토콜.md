### 확인된 사항 (사전 조사)

- `amaye15/barcodes-google-ocr`의 실제 규모는 **train 15.8k / test 3.96k (총 19.8k)** 다. 기획서의 "1.6만 / 4천"은 반올림 수준으로 맞다.
- 다만 스키마가 `pixel_values`(416px) / `label`(1 class) / `ocr`(가변 길이 리스트)다. **정답 바코드 번호가 보장된 필드가 아니고**, 이미지도 416px 실사 촬영본이라 이미 열화되어 있다.
- 따라서 이 데이터는 **탐지 학습용**으로 쓰고, 합성의 원본 재료로는 쓰지 않는다 (아래 4번).

## 2. 라벨링 도구와 품질 관리

### 도구

`labelImg`는 **회전 박스를 지원하지 않아** 배제한다.

| 후보 | 비고 | 선택 |
|---|---|---|
| **CVAT** | 회전 박스 지원. 다인 동시 작업 + 검수 기능. 무료 | 권장 |
| Roboflow | 더 쉽지만 무료 플랜 용량 제한 | |

### 작업 분배

1~2학년 4명 (김강민, 조아라, 이다현, 이아침). 952장 ÷ 4 = **1인당 238장**.

### 가이드라인 (라벨링 시작 전 필수)

**4명이 각자 판단하면 라벨이 일관되지 않고, 그러면 mAP 목표 달성이 불가능하다.** 아래 셋을 문서 1장으로 정해 공유한다.

| 항목 | 결정 |
|---|---|
| 바코드의 어디까지를 박스에 넣는가 (여백 포함 여부) | |
| 부분적으로 가려진 바코드는 라벨링하는가 | |
| **각도 기준선을 어디로 두는가** | |

**세 번째가 특히 중요하다.** 기준이 어긋나면 크롭이 90° 돌아간 상태로 학습되고, 디코더가 전혀 읽지 못한다.

### 품질 관리 결과

| 단계 | 결과 |
|---|---|
| 공동 작업 20장 — 기준 합의 | |
| 교차 검수 10% — **불일치율** | |
| 3학년 표본 검수 | |

**불일치율을 반드시 기록한다.** 나중에 mAP가 낮게 나올 때 원인이 모델인지 라벨인지 판단할 수 있는 유일한 근거다.

## 3. 실촬영 정답 확보 절차

기획서 4.6.2는 "출력 텍스트가 정답 번호와 완전히 일치"로 판정한다고 했으나 **정답을 어떻게 얻는지가 없었다.** 아래 순서를 확정한다.

```
① 송장을 평탄한 상태로 촬영  →  디코더로 정상 판독  →  정답 번호 기록
② 같은 송장을 구기고 비닐 씌우고 반사 유도  →  재촬영
③ 두 이미지를 같은 ID로 짝지어 저장
```

**순서를 바꾸면 구겨진 사진의 정답을 알 방법이 없어 데이터가 무효가 된다.** 사람이 눈으로 읽어 입력하는 것은 오타 위험 때문에 허용하지 않는다.

자동화 코드: `wemeet/data/ground_truth.py`

### 기록 시트 형식

```csv
id,ground_truth,symbology,damage_type,damage_level,lighting,note
F0001,8801234567890,CODE128,curvature,high,indoor_led,비닐 2겹
F0002,8801234567891,CODE128,glare,mid,indoor_led,
```

### `dev` / `eval` 분할

| 분할 | 비율 | 용도 | 여는 시점 |
|---|---|---|---|
| `dev` | 40% | 중간 점검, 도메인 갭 측정, 디버깅 | 언제든 |
| `eval` | 60% | **최종 평가 전용** | 11월 2주차에 한 번 |

**송장 단위로 나눈다.** 같은 송장의 다른 각도 사진이 양쪽에 들어가면 사실상 유출이다.

`eval`은 어떤 경우에도 학습·튜닝에 노출되지 않는다. 도메인 갭 대응으로 실촬영 데이터를 학습에 넣는 경우에도 `dev`만 쓴다.

### 개인정보

촬영 **전에** 수취인 이름·주소·연락처를 불투명 테이프로 차폐한다. 촬영 후 블러보다 확실하다. 원본은 private HF 저장소(`barcode-field`)에만 보관한다.

## 4. 합성 데이터 원본 재료 — 기획서 정정

기획서 4.2.1은 `barcodes-google-ocr`을 "역방향 합성의 원본 재료"로 지정했다. **이를 정정한다.**

위 1번에서 확인한 대로 그 데이터는 416px 실사 촬영본이라 **깨끗한 GT가 아니다.** 열화된 원본에 왜곡을 덧씌우면 정답 제어점이 가리키는 위치가 실제와 어긋난다.

### 합성 원본 렌더링 규격 — **미결정 · `0001` 확정 후**

깨끗한 바코드는 구해오는 것이 아니라 `python-barcode` 로 **직접 렌더링한다**. 그때 무엇을 어떻게 그릴지가 정해져야 한다.

**선행 조건**: `0001` 심볼로지 확정. 심볼로지에 따라 허용 문자, 문자당 모듈 수, 체크digit 자동 여부가 전부 달라지므로 그 전에는 정할 수 없다.

| 정할 것 | 후보 / 근거 |
|---|---|
| 번호 자릿수 | `0001` 현장 확인 결과를 따른다. 이것이 모듈 폭을 정하고, 모듈 폭이 복원 가능 여부를 정한다 |
| 문자 구성 | 숫자만 / 영문 혼용. Code128 은 둘 다 되지만 모듈 수가 다르다 |
| 접두사 패턴 | 실제 형식을 흉내낸다. **실제 번호를 그대로 쓰지 않는다** — 형식만 맞추고 뒷자리는 무작위 |
| `module_width` | 최종 픽셀 모듈 폭을 정한다. 촬영 해상도 요구사항과 맞물린다 |
| `module_height` | **반사 대응이 이 높이의 중복성을 쓴다.** 너무 낮으면 골라 쓸 행이 없다 |
| `quiet_zone` | 좌우 여백. 디코더가 시작·끝을 찾는 데 쓴다. 너무 좁으면 판독률이 떨어진다. **라벨링 규약(위 3단계)과 같은 값을 써야 한다** |
| `write_text` | 하단에 번호를 글자로 찍을지. 실제 송장에는 보통 있다 |
| dpi | 최종 해상도 |

담당: 데이터파트 / 기한: `0001` 확정 직후

### 촬영 해상도 요구사항 (2026-08-04 추가)

사전 실험(설계 문서 §8.4)에서 복원 가능 경계를 측정했다.

| 가로 압축(감긴 각도) | 가장자리 모듈 폭 | 판정 |
|---|---|---|
| 70° | 1.9 px | 보정하면 읽힘 |
| 84° | 0.6 px | **불가 — 정보 소실** |

**가장 압축된 지점에서 모듈 폭이 1~2px 이상 남아 있어야 한다.** 현장에서 화물이 얼마나 심하게 감겨 있는지 확인하고, 그 각도에서 모듈이 2px 이상 남도록 촬영 해상도를 정한다. 이 조건을 못 맞추면 어떤 모델로도 읽을 수 없다.

합성 데이터도 같은 기준을 따른다 — **모듈이 1px 이하가 되는 왜곡은 학습에 넣어도 배울 수 없다.**

#### 2026-08-28 정정 — 이 항목이 프로젝트 최우선 결정이다

재측정([합성 스파이크](../experiments/2026-08-28-synthesis-spike/README.md))에서 세 가지가 나왔다.

**① 지배 변수는 감긴 각도가 아니라 평탄 상태 모듈 폭이다.** Code128 은 심볼(11모듈) 안의
**상대 폭 비율**로 디코딩한다. 모듈이 5.5px 이면 심볼 하나가 60px 이라 어지간한 왜곡은
심볼 안에서 거의 균일해 비율이 안 깨진다. 2px 이면 심볼이 22px 이라 같은 왜곡이 비율을 무너뜨린다.

**② 그래서 Stage 2 가 값을 하는 비율이 해상도로 결정된다.** "1차 디코딩 실패 & 정답 제어점으로
보정하면 성공" 인 샘플의 비율(합성, zxing-cpp 기준):

| 평탄 모듈 폭 `d_m0` | 크롭 폭 | Stage 2 가 값을 하는 비율 |
|---|---|---|
| 1.6~2.2px | 260~340px | **12~18%** |
| 2.0~2.8px | 315~420px | 8% |
| 2.8~4.0px | 420~580px | 7% |

**현장이 모듈 5px 을 준다면 Stage 2 가 할 일이 거의 없고, 2px 근처라면 핵심이 된다.**
`0003`(모델 선정)과 `0005`(평가 지표)가 모두 이 값에 딸려 있다.

**③ "2px 이상" 기준은 2배 이상 보수적이다.** 합성만 놓고 보면 **0.8px 까지 복원된다.**
다만 노이즈·블러·반사가 전혀 없는 조건이므로 낙관적 상한이다.
2px 을 안전 마진으로 유지하되 **상수가 아니라 파라미터로 두고** 실촬영 베이스라인 후 조정한다.

**현장에서 반드시 확인할 것**: 화물 표면의 바코드가 사진에서 **가로 몇 px 을 차지하는가.**
각도보다 이 숫자가 먼저다. (`0001` 현장 확인 목록에도 추가)

대신 `python-barcode` 또는 `treepoem`으로 확정된 심볼로지(`0001`)를 **직접 렌더링**해 픽셀이 완벽한 원본을 생성한다. 정답 번호도 우리가 아는 값이 된다.

#### 대체 방법 — 높이장에서 기하와 광학을 함께 유도한다

관측 좌표 위의 높이장 기울기 `(z_x, z_y)` 하나를 설계 대상으로 삼는다. 여기서 전부 나온다.

| 필요한 것 | 유도 |
|---|---|
| 압축률 | `m = 1/√(1+z_x²) ≤ 1` — 종이는 늘어나지 않으므로 구조적으로 보장된다 |
| 매핑 | `s = np.cumsum(1/m)` (**`cumsum(m)` 이 아니다** — 설계 문서 §13 정정) |
| 정답 제어점 | 펴진 격자에서 `s` 의 역보간 |
| 음영·정반사 | 법선 `n ∝ (−z_x, −z_y, 1)` 로 Blinn-Phong |

**정반사는 곱이 아니라 더한다.** 곱하면 검은 막대가 절대 지워지지 않는다(실측 평균 밝기 0.005).
실제 비닐 반사는 막대를 하얗게 덮으므로 더하기가 맞다(0.275, 24%가 덮임).
그리고 **하이라이트가 좁으면 디코더가 우회한다** — 정보를 죽이려면 넓어야 한다(Blinn-Phong 지수 40 근처).

왜곡 성분은 원통·물결(`sine`)·접힘(`crease`) 셋이고, 구김은 `sine` 을 옥타브로 겹치면 나온다.
세기는 전부 **최대 기울기**라는 하나의 단위로 표현되므로(원통 `tanθ`, 물결 `2πA/λ`, 접힘 `tanα`)
판독 하한에서 나오는 예산 `|z_x|max ≤ √((d_m0/c_min)² − 1)` 을 선형으로 나눠 쓴다.
실측에서 **물결 상한 `A/λ ≤ 0.41` 이 정확히 경계**로 확인됐다(0.30 에서 보정 성공, 0.41 에서 실패).

증강(크롭 여백·회전 잔차)은 이미지와 **밀집 대응장 `G`(펴진→관측)를 함께 변환**하고
제어점은 맨 마지막에 `G` 에서 한 번 뽑는다. 제어점 좌표를 직접 변환하는 코드를 두면 안 된다.
여백은 **−2% ~ +15%** 로 제한한다 — 바코드 본체를 잘라먹으면 start/stop 이 사라져 샘플이 무효다
(실측: −2% 는 보정 후 성공, −6% 는 실패).

파라미터는 실촬영 `dev` 분할과 비교해가며 조정한다. 이것이 도메인 갭을 줄이는 유일한 방법이다.
