## 왜 비교하는가 — 기획서와 다른 부분

기획서는 pyzbar를 전제한다. 그런데 검출·기하 추정 모델은 후보를 비교해 고르기로 했으니(`0002`, `0003`) **같은 논리가 디코더에도 적용되어야 한다.**

그리고 이건 단순한 형평성 문제가 아니다.

> **디코더만 바꿔서 성공률이 크게 오르면, 기획서 4.6.2가 측정하려는 "AI 기하 보정이 기여한 순수 향상폭"이 실제보다 부풀려진다.**

극단적으로는 **AI 없이 디코더 교체만으로 목표를 달성**할 수도 있다. 그렇다면 프로젝트 전제 자체를 다시 봐야 한다. 11월 심사에서 "왜 pyzbar만 썼나"라는 질문에 답할 근거도 필요하다.

비용은 하루다. 평가 코드는 같고 호출부만 바꾼다.

## 후보

| 후보 | 설치 | 비고 |
|---|---|---|
| **pyzbar** (ZBar 바인딩) | `pyzbar` | 기획서 안. 오래된 라이브러리이고 회전·왜곡에 특히 약하다고 보고된다 |
| **zxing-cpp** | `zxing-cpp` | ZXing의 C++ 재작성판. 파이썬 바인딩 제공 |
| **OpenCV `barcode`** | `opencv-python>=4.8` | `cv2.barcode.BarcodeDetector`. **4.8부터 main 패키지에 포함** (그 이전은 `opencv-contrib-python` 필요) |

세 번째의 버전 조건을 놓치면 "왜 `cv2.barcode`가 없지"로 시간을 쓴다.

참고: [Nature Sci Rep 2025 논문](https://www.nature.com/articles/s41598-025-29720-w)이 OpenCV `barcode`로 양호 조명 98.5%, 저조도 85.2%, 부분 가림 78.3%를 보고한다.

## 재시도 파라미터 탐색 순서

기획서 4.3.3은 "사전 정의된 탐색 순서에 따라 최대 3회 재시도"라고만 하고 **순서를 정의하지 않았다.** 순서가 성능과 지연을 모두 좌우하므로 아래를 초기값으로 확정한다.

| 시도 | 변경하는 것 | 노리는 실패 원인 |
|---|---|---|
| 0차 (최초) | CLAHE + 적응형 이진화 기본값 | — |
| 1차 재시도 | **이진화 임계값을 낮춤** | 반사로 밝아져 바가 사라진 경우 |
| 2차 재시도 | **이진화 임계값을 높임** | 그림자로 어두워져 흰 여백이 사라진 경우 |
| 3차 재시도 | **모폴로지 커널 확대 + 대비 강화** | 주름으로 바가 끊어진 경우 |

**임계값을 먼저 낮추는 이유**: 이 프로젝트의 1순위 훼손이 비닐 반사이고, 반사는 밝아지는 방향의 손실이다. 흔한 원인부터 시도하면 평균 재시도 횟수가 줄어 지연 예산에 유리하다.

### 재시도할 때 기하 추정은 다시 돌리지 않는다 — 보정은 다시 한다

2026-08-04에 방침이 바뀌었다. 두 단계의 비용이 완전히 다르기 때문이다.

| | 비용 | 재시도에서 |
|---|---|---|
| 기하 추정 (AI) | 150 ms | **다시 돌리지 않는다.** 4번이면 예산이 무너진다 |
| 기하 보정 (OpenCV) | 20 ms | **다시 한다.** 3번 해도 60ms다 |

그래서 재시도가 실질적인 의미를 갖게 됐다 — 같은 `GeometryField`를 **다르게 적용**해서 다시 읽는다. 바꿀 후보는 보간법(`INTER_CUBIC` → `LANCZOS4` → `LINEAR`), 이진화 임계값, 제어점 변위 스케일이다.

이전 방침은 "이진화와 디코딩만 다시 한다"였다. 복원이 250ms라 다시 돌릴 수 없었고, 그래서 재시도에서 바꿀 것이 이진화 설정뿐이었다.

기획서 4.3.3도 재시도 루프를 "학습된 모델의 출력 이후 단계에서 작동하는 규칙 기반 보완 장치"로 규정한다.
