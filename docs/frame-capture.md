# 연속 프레임 수집 실험

## 바코드 추적 전환 설계 — 2026-10-26

대상은 쿠팡 물류센터다. 작업 브랜치 `sw/barcode-track-capture`는 기존 실험의
`966d480`에서 시작하며 기반 통합 커밋 `f601c9e`와 PR #27·#28·#29를 포함한다.
아래 예산은 설계 가정이다. 실제 구현 및 평가 결과는 다음 절에 구분한다.

| 박스 확보 | 효과 | 비용·승인 |
|---|---|---|
| (가) `DetectedBarcode.bbox_xywh_original = None` 추가 | 실제 바코드로 시작하고 ROI 선명도로 선택 | 원본 픽셀의 OBB 외접 사각형 `(x,y,w,h)`. AI 검출 반환부·공유 스키마 변경 전 명시적 승인 필요 |
| (나) SW 배경 차이 blob | 승인 없이 입력·추적·물품별 결과 구조 구현 | 손·그림자·벨트·조명에 취약. 바코드 ROI로 간주할 수 없음 |
| (다) SW에서 YOLO 내부 결과 직접 읽기 | 스키마 수정 없이 좌표 획득 | AI 내부 결합·전처리 중복 때문에 미채택 |

사용자가 2026-10-26 이 대화에서 (가)의 좌표 필드·AI 검출 반환부 변경을 명시적으로
승인했다. 해당 범위로 구현했으며 별도 AI 알고리즘 변경은 없다. 박스 공급원은
`observe(frame) -> boxes | None`으로 분리한다. `None`은 이번 프레임 검출 생략,
빈 목록은 실제 관측했지만 없음이다. 추적기와 판독기는 HTTP/카메라 API를 모른다.

브라우저는 1920×1080 이내, JPEG 0.90, 최대 8fps를 유지하고 4장/0.5초로 전송한다.
전송 묶음과 물품 구간은 독립이다. 트랙 시작은 관측 박스, 유지는 시간 기반 속도 예측과
거리·크기 연결, 종료는 연속 미관측 또는 예측된 화면 이탈이다. 시각 역행은 거부하고
긴 입력 공백은 기존 트랙을 종료해 다른 통과와 섞지 않는다. 정지한 손은 배경에 흡수하지 않는다.
번호는 연결 키로 쓰지 않으며 재등장은 새 ID다. 단일 활성 트랙만 지원하되 공급원은 목록을
반환한다. 가까운 물품 병합, 가림 후 분리, 역방향 손 이동, 조명 변화를 실패 사례로 남긴다.

트랙별 후보를 메모리에서 제한하고 종료 후 최대 3장에 기존 `process_batch` 규칙을 적용한다.
ROI는 실제 바코드 박스 공급원이 있을 때만 사용한다. blob 범위를 바코드 ROI라고 표시하지
않는다. 기존 4개 판독 상태와 단일 이미지 pipeline/API는 유지한다. 결과는 트랙당 한 번,
재요청은 같은 ID로 중복 표시하지 않는다. 추적 수집과 느린 판독을 분리하고 유한 대기열이
넘치면 누락을 명시한다. 세션 만료·중지 시 이미지 메모리를 해제한다. 이미지와 번호는
파일·로그·영구 브라우저 저장소에 쓰지 않는다.

CPU 검출 주기의 초기 제안은 8fps 중 N=16(약 2초마다)이다. 0.65~1.1초/검출이면
검출에만 32.5~55%의 직렬 실행 시간을 쓰고, 트랙 판독 최대 3회에 2.1~7.5초가 추가된다.
2초보다 짧은 통과는 시작 검출부터 놓칠 수 있으므로 개발 시험은 느린 손 이동으로 한다.
확정 전에는 CPU 연속 전수 판독을 보장할 수 없다. 이 추적 방식의 GPU 성능은 미측정이며
가령 검출 50ms 이하가
확인될 때만 4~8Hz 재검출을 검토한다. GPU 설치·가속 구현은 이번 범위 밖이다.

기존 고정 1초/8장 모드를 그대로 선택 가능하게 둔다. 같은 입력 시각·픽셀·처리 예산에서
물품당 정확 판독, 오독 확정, 확인 부족, 누락, 중복, 통과 후 지연, 처리량을 비교한다.
합성 영상은 기존 정답 장면을 메모리에서 이동시키고 간격·빈 구간·동일 상품 반복·가까운
물품을 포함한다. 오프라인 무제한 처리와 실시간 처리 예산을 구별한다. 현재 폴더에는
실제 사진 6장만 있으며 휴대폰 영상은 없다. 실영상 통과 성능은 미평가로 남긴다.

## 추적 구현과 설정

- 화면의 **수집 방식**에서 바코드 추적(기본), 기존 고정 1초, 움직임 덩어리 추적을 선택한다.
  전환은 이전 세션을 닫고 새 세션을 시작한다. 고정 창에서만 장면 변화 필터를 사용한다.
- `wemeet/sw/tracking/sources.py`: 바코드 재검출 2000ms 간격. GPU 경로는 추가하지 않았다.
  motion 모드는 320×180 고정 배경 차이이며 70% 이상 전역 변화는 관측 없음으로 처리한다.
- `core.py`: 일정 속도 예측과 중심 거리·면적 비율로 단일 트랙을 연결한다. 초기 속도가 없을
  때는 넓게 연결하므로 서로 가까운 물품을 합칠 수 있다. 두 관측 사이 후보 ROI는 보간해서
  수정한다. 예측 ROI도 오차가 있으므로 검출 신뢰도나 품질 점수를 정답 확률로 해석하지 않는다.
- 종료: 바코드 관측 실패 2회(motion 3회), 마지막 관측 후 4500ms, 예측 박스가 화면 밖,
  2500ms 초과 입력 공백, 해상도 변경, 연결 실패. 30초 정지는 한 번 종료한 뒤 실제 미관측까지
  새 결과를 만들지 않는다. 중지·탭 숨김·세션 만료 때 미완료 트랙은 폐기한다.
- 후보는 첫/마지막을 포함해 시간적으로 분산된 최대 8장이다. 가장 촘촘한 중간 후보를 먼저
  버리므로 구간 전체에서 최적이었던 프레임을 보존한다고 보장할 수 없다. 최종 선택은 변경
  없는 `select_best_frame`의 바코드 ROI 모드를 사용한다. motion/기준선은 전체 프레임이다.
- 서버는 세션 최대 2개, 활성 트랙 1개/세션, 판독 대기 2개/세션, 공통 추론 슬롯 1개다.
  판독 중에도 프레임 수신·예측을 계속하고, 슬롯이 바쁘면 재검출을 생략해 화면에 집계한다.
  대기열 초과는 해당 트랙의 `unread/queue_full` 결과를 한 번 남긴다. 아직 검출하지 못한 물품의
  수는 알 수 없으므로 '검출 건너뜀'을 '누락 물품 수'로 표시하지 않는다.
- 브라우저는 전송 1개 + 대기 묶음 2개, 2500ms 지난 묶음은 폐기한다. 서버의 결과는 최대
  10개/16MiB, 세션은 마지막 프레임 업로드 후 30초에 만료한다. 결과 순번 커서로 새 결과만
  내려받고 트랙 ID로 화면 중복을 막는다. 번호로 합치지 않는다. 실행 중인 Python 판독은
  강제 취소할 수 없으며 종료 후 참조가 해제된다.
- multipart 전체 15MiB/최대 1080p 검증 후 메모리에서만 JPEG를 읽는다. 임시 파일로 넘어가는
  기본 spool 임계값도 전체 용량보다 크게 두었다. 이미지·판독값은 파일/로그에 남기지 않는다.

`POST /api/track-frames`는 기존 multipart 형식을 확장한다: `window_ms=500`,
`sequence`(증가 정수), `captured_at_ms`(브라우저 단조 시각), `box_source=barcode|motion`,
프레임 1~4장, `offset_ms`는 0 이상 500 미만이다. `/api/decode-burst`의 1000ms 계약은 유지한다.
`GET /api/tracking/{session_id}?after={result_sequence}`로 상태/새 결과,
`DELETE /api/tracking/{session_id}`로 폐기한다. 닫힌 세션의 늦은 업로드는 60초간 거부한다.
트랙 결과는 기존 4개 상태와 함께 track ID, 시작/종료 시각, 종료 이유, 박스 공급원,
후보·시도 수, 선택 범위(ROI/전체), 대표 이미지, 단계 시간을 전달한다.

## 추적 평가 — 2026-10-26

재현 도구는 `scripts/evaluate_tracking.py`, 집계 결과는
`docs/benchmark/tracking-2026-10-26.json`이다. `downloads/benchmark-v1`의
`first_ok` 장면 3개에서 정답과 크롭을 읽어 **파일을 만들지 않고 메모리에서** 이동시켰다.
39초/312프레임, 1920×1080/JPEG90/8fps, 물품 6회 통과다. 5초 통과 3회, 4초 통과 2회,
1초 통과 1회이며 빈 구간, 같은 상품 재등장, 0.5초 간격의 가까운 물품을 포함한다.
두 모드는 같은 시각·픽셀을 받는다. 기준선은 브라우저의 배경/직전 프레임 변화 규칙을
8fps로 재현한다. 축소 보간은 OpenCV를 쓰므로 브라우저 canvas 픽셀과 완전히 같지는 않다.

**판독값은 실제 CPU 모델 결과이고, 큐와 지연은 비용 가정에 따른 시뮬레이션이다.**
초기 실측 비용 기반 재생에서 검출/판독 호출 중 300초 이상 지연이 섞여 입력 누락까지
왜곡됐다. 원인은 확인하지 못했으며 그 실행은 성능 비교에서 제외했다. 최종 재생은
검출 1000ms, 판독 시도당 2000ms, 선택 후보당 39ms를 동일 직렬 슬롯에 부과한다.
검출은 2초 간격이고 판독이 슬롯을 사용하면 건너뛴다. 호스트 대기가 투표 수에 영향을
주지 않도록 평가 실행에만 실제 경과 9초 제한을 해제했다. 최대 3장·동일 번호 2장 확인은
그대로이며 제품 코드의 9초 예산도 유지한다. 네트워크/브라우저 전송 대기열은 모사하지 않는다.
따라서 이 표는 실제 컨베이어 처리 성능이나 현장 정확도가 아니다.

CPU 시간은 여러 스레드가 쓴 시간을 합하므로 재생 벽시계 시간보다 클 수 있다.
입력 처리량은 모든 프레임에 검출/판독을 실행한 속도가 아니다. 누락·건너뜀을 포함한
오프라인 재생 처리량이며, 실시간 30fps 판독 성능으로 해석하면 안 된다.
최종 실행의 판독 묶음 실제 시간 중앙값은 기준선 1.223초, 추적 1.012초,
추적용 추가 검출 중앙값은 0.260초다. 단순 합성 배경·워밍업 후의 결과여서 기존 웹캠
0.7~2.5초/프레임 실측을 대체하지 않는다. 최종 실행에는 30초 초과 호출이 없었다.

물품 배정은 최초 선택 프레임의 합성 물품 ID로 하고 번호로 합치지 않는다. 정답·판독값은
메모리에서만 대조하며 저장 JSON에는 장면별 번호와 이미지가 없다. 추적은 재검출 20번의
기회 중 11번을 판독 슬롯 점유로 건너뛰었다. 결과가 없는 두 보통 속도 물품과 1초 통과
물품이 생겼다. 중복 감소와 함께 누락 증가를 그대로 보고하며 추적 우위를 주장하지 않는다.

```powershell
# 로컬 가중치 환경 변수가 있으면 기존 WEMEET_*_WEIGHTS 설정을 사용한다.
uv run python -m scripts.evaluate_tracking --output docs/benchmark/tracking-2026-10-26.json
```

이 변조는 파일을 수정하지 않으며 종료 후 정상 구현으로 다시 통과시킨다.
화면 내 모듈 구문도 Node로 검사한다. 실제 카메라 UI 운전이나 10분 운전 시험을 대신하지 않는다.

최종 검사: `ruff check`·`ruff format --check` 통과, import-linter 계약 4개 유지,
Python **266개 통과/10개 건너뜀**, JavaScript **22개 통과**. 건너뛴 가중치 의존 검사는
통과로 세지 않았다. 기존 Starlette TestClient 의존성의 deprecation 경고 1개가 남아 있다.

### 남은 한계와 사람이 결정할 사항

- `downloads/real-captures`에는 사진 6장만 있어 요청의 휴대폰 영상 비교는 수행하지 못했다.
  쉬운 정답 장면 3개의 이동 합성은 독립 표본이 아니며 반사막·초점·노출·실제 운동 흐림을
  대표하지 않는다. 이미지/번호를 새 파일로 남기지 않는 조건도 유지했다.
- 박스 예측/초기 넓은 연결은 손의 방향 전환·가림·가까운 물품에 약하다. 다중 동시 바코드는
  지원하지 않는다. 잘못 합쳐진 구간에서 같은 오독이 두 번 나오면 교차 확인도 막지 못한다.
  best_frame의 포화 반사 항은 변경하지 않았으며 옅어진 반사막에 대한 한계도 그대로다.
- 추적 모드는 실험용이다. CPU에서 판독 중 새 물품을 놓치는 구조가 남아 있다. 먼저 실제
  통과 시간과 최소 물품 간격을 정하고 재검출 주기·후보 수·판독 예산을 함께 조정해야 한다.
  GPU 성능 및 가속 구현은 이번 작업에서 측정·추가하지 않았다.
- 네트워크가 30초 이상 끊겨 세션이 만료하면 자동 판독을 중지 후 다시 시작해야 한다.
  늦은 업로드의 부활 방지는 60초 보관된 종료 ID 범위다. 결과 보관 한도를 넘기는 장기
  통신 장애에서는 이전 결과를 다시 가져올 수 없다.
- 다음 사람이 결정할 것은 시험 물품 속도/간격, 허용 누락·중복·지연, 정답 있는 실영상
  확보와 장시간 카메라 시험이다. 공유 계약 변경은 이 대화에서 승인받은 범위로 완료했다.

## 손으로 움직이는 시험

1. 카메라를 고정하고 빈 촬영 영역을 준비한다.
2. **카메라 · 자동 판독 시작**을 누른다. 이후 물품마다 누르는 버튼은 없다.
3. 자동 노출이 안정된 뒤, 필요하면 **빈 배경 다시 등록**을 누른다.
4. 하나의 바코드를 카메라 앞으로 천천히 이동시킨다. 잠시 멈췄다가 다시 움직여도 된다.
5. 미리보기와 선택 이미지가 서로 구분되는지, 수집 수·판독 시도 수·교차 확인 상태를 확인한다.
6. 화면에서 물체를 완전히 뺀 뒤 다른 번호를 보여 준다. 같은 상품을 다시 보여 주는 것도 시험한다.
7. 움직임 필터가 후보를 놓치는지 비교하려면 **장면 변화가 있는 구간만 판독**을 해제한다.
8. **자동 판독 중지**는 전송·샘플링만 멈추고 미리보기는 유지한다. **카메라 중지**는 장치를 끈다.

브라우저가 백그라운드가 되면 자동 판독을 일시 중지하고, 돌아오면 새 세션으로 재개한다.
이때 배경이 다시 등록되므로 물체를 뺀 상태로 돌아오거나 빈 배경을 재등록한다.
카메라 분리·권한 거부는 화면에 표시하며, 장치를 다시 연결하고 시작 버튼을 누른다.
브라우저 자체의 권한 거부를 프로그램이 우회하지 않는다.

## 실제 동작과 한계

- 영상은 1920×1080, 30fps를 요청한다. 브라우저가 제공한 실제 영상에서 1초마다 최대 8개
  서로 다른 프레임을 JPEG 0.90으로 캡처한다. 큰 영상은 최대 1920×1080 안으로 축소한다.
  부족한 프레임은 복제하지 않는다. 영상 정지나 긴 지연이 있으면 불완전한 구간을 버린다.
- 작은 160×90 영상의 빈 배경 대비 변화와 이전 프레임 대비 변화로 업로드 후보를 정한다.
  이는 바코드 검출이 아니다. 조명이나 벨트 무늬가 바뀌면 오작동할 수 있다.
  배경은 물체가 멈춰 있는 동안 자동으로 갱신하지 않는다.
- `select_best_frame(frames, bboxes=None)`을 그대로 호출한다. 선택 프레임을 제외한 나머지에
  다시 호출하므로 점수는 각 호출의 후보 집합 안 상대값이다. 점수는 성공 확률이 아니다.
- 선택한 **원본 전체 프레임**에 기존 `pipeline.run()`을 적용한다. 최대 3장을 시도한다.
  같은 픽셀의 복제 프레임은 중복 표로 세지 않고, 시도 간 촬영 시각은 최소 100ms 떨어뜨린다.
- 2장의 번호 일치 → `confirmed`, 1장만 읽힘 → `provisional`, 서로 다른 번호 → `conflict`,
  모두 실패 → `unread`. 충돌을 단순 다수결로 확정하지 않는다. 문자열의 앞자리 0을 보존한다.
  두 번 같은 오독이 날 수도 있으므로 `confirmed`는 정답 보장이 아니다.
- 처리 예산은 9초이며 다음 시도 전에 예상 비용(판독 2.5초 + 후보당 선택 39ms)을 확보한다.
  실행 중 파이프라인을 강제 중단하지 않는다. 실제 시간은 예산을 넘을 수 있다.
- 브라우저는 요청 1개 + 대기 활동 묶음 1개를 유지한다. 새 활동 묶음이 대기를 교체하면
  건너뜀 수를 올린다. 빈 묶음은 활동 후보를 덮어쓰지 않는다. 15초 넘게 지난 후보도 버린다.
  서버는 단일 이미지와 묶음 요청에 공통 추론 슬롯을 쓴다. 바쁘면 429, 준비 전이면 503이다.
- 1초 묶음은 물품 추적 결과가 아니다. 두 물품이 한 구간에 섞일 수 있고 같은 물품이 여러 구간에
  나타날 수 있다. 서로 다른 묶음의 표를 합치지 않으며, 화면 숫자는 물품 처리량이 아니다.
- CPU가 유입 속도를 따라가지 못하면 통과한 물품을 놓칠 수 있다. GPU의 실측 속도와 물품 간격,
  구간 경계/추적 개선 전에는 컨베이어 전수 판독을 보장하지 않는다.
- 이미지는 디스크나 로그에 저장하지 않는다. 브라우저 이력은 최대 10개, 서버 중복 응답 캐시는
  최대 4개/16MiB/60초(다음 요청 때 만료 정리)로 제한한다. 탭을 새로 열면 브라우저 이력은 사라진다.

## API

`POST /api/decode-burst`: multipart의 `manifest` JSON 문자열과 반복되는 `frames` JPEG 파일.
파일과 manifest 프레임 배열의 순서가 대응한다. 1~8장, 전체 15MiB, 프레임당 1920×1080 픽셀 수
이하를 허용한다. 모든 프레임 해상도가 같고 `offset_ms`는 0 이상 1000 미만으로 증가해야 한다.

```json
{
  "session_id": "unique-session",
  "batch_id": "b-1",
  "source_id": "browser",
  "window_ms": 1000,
  "jpeg_quality": 0.9,
  "trigger": "activity",
  "frames": [
    {"frame_id": "f-1", "offset_ms": 0, "width": 1920, "height": 1080}
  ]
}
```

같은 session/batch ID와 내용의 재요청은 캐시가 남아 있으면 같은 결과를 반환한다.
동일 ID로 내용을 바꾸면 409, 실행 중이면 429다. HTTP 취소가 모델 실행을 취소하지는 않는다.
응답의 `ok`는 교차 확인 여부다. 개별 시도의 성공 여부는 `attempts`와 대표 프레임의 `result`에서
확인한다. `frame_attempt_count`와 프레임 내부 `retry_count`는 다른 값이다.

이력·실시간 결과·상세 화면은 판독 성공과 교차 확인을 구분한다. 1장만 성공한 경우
**판독 성공 · 교차 확인 부족**, 2장 일치 시 **판독 성공 · 교차 확인 완료**, 충돌 시
**번호 충돌 · 확정 보류**, 모두 실패하면 **미판독**으로 표시한다. 수집·시도·일치 장수와
미검출/검출 후 디코딩 실패 수를 표시한다. **추가 확인** 탭에서 이력을 선택하면 해당
묶음의 프레임별 결과와 종료 이유를 볼 수 있다. 대표 이미지 하나만으로 전체 시도를 판단하지 않는다.

브라우저 화면을 직접 관찰하기 어려울 때는 진단 로그를 켜서 실행한다.

```powershell
uv run python -c "import logging, uvicorn; logging.basicConfig(level=logging.INFO); uvicorn.run('wemeet.sw.server:app', host='127.0.0.1', port=8001)"
```

`wemeet.sw.server.burst`의 `decode_burst` 로그는 이미지·바코드 번호·클라이언트 ID를 제외하고
장수, 단계별 시간, 실패 이유를 남긴다. `text_group`은 각 묶음 안에서만 붙이는 번호다.
`[1, 1]`은 두 프레임의 같은 판독값, `[1, 2]`는 충돌, `null`은 판독 실패이며 서로 다른 묶음의
그룹 번호를 비교하면 안 된다. 동일 요청의 캐시 응답은 새로운 판독 로그를 남기지 않는다.

`primary_frame_id`/`primary_image`는 최초 선택, `representative_frame_id`/`result`는 최종 대표
프레임이다. 실패 뒤 성공한 경우 서로 다를 수 있다. `selection`, `pipeline`, `processing`,
`server` 시간은 서버 시계로 측정한다. 최초 수집부터 응답까지의 시간은 브라우저 시계로 측정한다.

## 검증

```powershell
uv run ruff check .
uv run ruff format --check .
uv run lint-imports
uv run pytest -q

```

자동 테스트는 합성 이미지/가짜 모델과 브라우저 상태 로직을 검증한다. 실물 카메라 성능 검증은

대기열이 증가하지 않는지도 확인한다.

기준선 구현 당시 변경 범위는 SW의 입력 어댑터·묶음 처리·서버·화면이었다. 이번 추적 전환의
승인된 좌표 계약 변경은 앞 절에 기록했다. AI 선택 알고리즘과 단일 프레임 파이프라인은 유지한다.
