# 연속 프레임 수집 실험

실험 브랜치: `codex/continuous-frame-capture`. 기반 통합 커밋은
`f601c9e1289a6bbb767e37e094ea7d7361686c5e`이며 PR #27, #28, #29를 포함한다.
main에는 적용하지 않는다. 실험 전 main 커밋은 `d1e7d243e9beff638a422aebc9c17abdc2dee3c5`다.

## 실행

```powershell
uv sync --frozen
uv run uvicorn wemeet.sw.server:app --host 127.0.0.1 --port 8001
```

브라우저에서 `http://localhost:8001`을 연다. 카메라를 지원하는 Chrome/Edge 등에서
카메라 권한을 허용한다. LAN 주소로 접근할 때는 HTTPS가 필요하다.
서버는 모델을 미리 불러오고 워밍업한다. `/api/health`의 `ready=true`를 확인한다.
모델 준비 실패 시 가중치 경로나 HF 연결을 확인한 뒤 서버를 다시 시작한다.
여러 uvicorn worker를 쓰면 추론 슬롯과 중복 캐시가 프로세스마다 생기므로,
이 실험은 **단일 프로세스, worker 1개**로 실행한다.

## 손으로 움직이는 시험

1. 카메라를 고정하고 빈 촬영 영역을 준비한다.
2. **카메라 · 자동 판독 시작**을 누른다. 이후 물품마다 누르는 버튼은 없다.
3. 자동 노출이 안정된 뒤, 필요하면 **빈 배경 다시 등록**을 누른다.
4. 하나의 바코드를 카메라 앞으로 천천히 이동시킨다. 잠시 멈췄다가 다시 움직여도 된다.
5. 미리보기와 선택 이미지가 서로 구분되는지, 수집 수·판독 시도 수·교차 확인 상태를 확인한다.
6. 화면에서 물체를 완전히 뺀 뒤 다른 번호를 보여 준다. 같은 상품을 다시 보여 주는 것도 시험한다.
7. 움직임 필터가 후보를 놓치는지 비교하려면 **장면 변화가 있는 구간만 판독**을 해제한다.
8. **자동 판독 중지**는 전송·샘플링만 멈추고 미리보기는 유지한다. **카메라 중지**는 장치를 끈다.

브라우저가 백그라운드가 되면 자동 판독을 일시 중지하고, 돌아오면 새 세션으로 재개한다.
이때 배경이 다시 등록되므로 물체를 뺀 상태로 돌아오거나 빈 배경을 재등록한다.
카메라 분리·권한 거부는 화면에 표시하며, 장치를 다시 연결하고 시작 버튼을 누른다.
브라우저 자체의 권한 거부를 프로그램이 우회하지 않는다.

## 실제 동작과 한계

- 영상은 1920×1080, 30fps를 요청한다. 브라우저가 제공한 실제 영상에서 1초마다 최대 8개
  서로 다른 프레임을 JPEG 0.90으로 캡처한다. 큰 영상은 최대 1920×1080 안으로 축소한다.
  부족한 프레임은 복제하지 않는다. 영상 정지나 긴 지연이 있으면 불완전한 구간을 버린다.
- 작은 160×90 영상의 빈 배경 대비 변화와 이전 프레임 대비 변화로 업로드 후보를 정한다.
  이는 바코드 검출이 아니다. 조명이나 벨트 무늬가 바뀌면 오작동할 수 있다.
  배경은 물체가 멈춰 있는 동안 자동으로 갱신하지 않는다.
- `select_best_frame(frames, bboxes=None)`을 그대로 호출한다. 선택 프레임을 제외한 나머지에
  다시 호출하므로 점수는 각 호출의 후보 집합 안 상대값이다. 점수는 성공 확률이 아니다.
- 선택한 **원본 전체 프레임**에 기존 `pipeline.run()`을 적용한다. 최대 3장을 시도한다.
  같은 픽셀의 복제 프레임은 중복 표로 세지 않고, 시도 간 촬영 시각은 최소 100ms 떨어뜨린다.
- 2장의 번호 일치 → `confirmed`, 1장만 읽힘 → `provisional`, 서로 다른 번호 → `conflict`,
  모두 실패 → `unread`. 충돌을 단순 다수결로 확정하지 않는다. 문자열의 앞자리 0을 보존한다.
  두 번 같은 오독이 날 수도 있으므로 `confirmed`는 정답 보장이 아니다.
- 처리 예산은 9초이며 다음 시도 전에 예상 비용(판독 2.5초 + 후보당 선택 39ms)을 확보한다.
  실행 중 파이프라인을 강제 중단하지 않는다. 실제 시간은 예산을 넘을 수 있다.
- 브라우저는 요청 1개 + 대기 활동 묶음 1개를 유지한다. 새 활동 묶음이 대기를 교체하면
  건너뜀 수를 올린다. 빈 묶음은 활동 후보를 덮어쓰지 않는다. 15초 넘게 지난 후보도 버린다.
  서버는 단일 이미지와 묶음 요청에 공통 추론 슬롯을 쓴다. 바쁘면 429, 준비 전이면 503이다.
- 1초 묶음은 물품 추적 결과가 아니다. 두 물품이 한 구간에 섞일 수 있고 같은 물품이 여러 구간에
  나타날 수 있다. 서로 다른 묶음의 표를 합치지 않으며, 화면 숫자는 물품 처리량이 아니다.
- CPU가 유입 속도를 따라가지 못하면 통과한 물품을 놓칠 수 있다. GPU의 실측 속도와 물품 간격,
  구간 경계/추적 개선 전에는 컨베이어 전수 판독을 보장하지 않는다.
- 이미지는 디스크나 로그에 저장하지 않는다. 브라우저 이력은 최대 10개, 서버 중복 응답 캐시는
  최대 4개/16MiB/60초(다음 요청 때 만료 정리)로 제한한다. 탭을 새로 열면 브라우저 이력은 사라진다.

## API

`POST /api/decode-burst`: multipart의 `manifest` JSON 문자열과 반복되는 `frames` JPEG 파일.
파일과 manifest 프레임 배열의 순서가 대응한다. 1~8장, 전체 15MiB, 프레임당 1920×1080 픽셀 수
이하를 허용한다. 모든 프레임 해상도가 같고 `offset_ms`는 0 이상 1000 미만으로 증가해야 한다.

```json
{
  "session_id": "unique-session",
  "batch_id": "b-1",
  "source_id": "browser",
  "window_ms": 1000,
  "jpeg_quality": 0.9,
  "trigger": "activity",
  "frames": [
    {"frame_id": "f-1", "offset_ms": 0, "width": 1920, "height": 1080}
  ]
}
```

같은 session/batch ID와 내용의 재요청은 캐시가 남아 있으면 같은 결과를 반환한다.
동일 ID로 내용을 바꾸면 409, 실행 중이면 429다. HTTP 취소가 모델 실행을 취소하지는 않는다.
응답의 `ok`는 교차 확인 여부다. 개별 시도의 성공 여부는 `attempts`와 대표 프레임의 `result`에서
확인한다. `frame_attempt_count`와 프레임 내부 `retry_count`는 다른 값이다.

이력·실시간 결과·상세 화면은 판독 성공과 교차 확인을 구분한다. 1장만 성공한 경우
**판독 성공 · 교차 확인 부족**, 2장 일치 시 **판독 성공 · 교차 확인 완료**, 충돌 시
**번호 충돌 · 확정 보류**, 모두 실패하면 **미판독**으로 표시한다. 수집·시도·일치 장수와
미검출/검출 후 디코딩 실패 수를 표시한다. **추가 확인** 탭에서 이력을 선택하면 해당
묶음의 프레임별 결과와 종료 이유를 볼 수 있다. 대표 이미지 하나만으로 전체 시도를 판단하지 않는다.

브라우저 화면을 직접 관찰하기 어려울 때는 진단 로그를 켜서 실행한다.

```powershell
uv run python -c "import logging, uvicorn; logging.basicConfig(level=logging.INFO); uvicorn.run('wemeet.sw.server:app', host='127.0.0.1', port=8001)"
```

`wemeet.sw.server.burst`의 `decode_burst` 로그는 이미지·바코드 번호·클라이언트 ID를 제외하고
장수, 단계별 시간, 실패 이유를 남긴다. `text_group`은 각 묶음 안에서만 붙이는 번호다.
`[1, 1]`은 두 프레임의 같은 판독값, `[1, 2]`는 충돌, `null`은 판독 실패이며 서로 다른 묶음의
그룹 번호를 비교하면 안 된다. 동일 요청의 캐시 응답은 새로운 판독 로그를 남기지 않는다.

`primary_frame_id`/`primary_image`는 최초 선택, `representative_frame_id`/`result`는 최종 대표
프레임이다. 실패 뒤 성공한 경우 서로 다를 수 있다. `selection`, `pipeline`, `processing`,
`server` 시간은 서버 시계로 측정한다. 최초 수집부터 응답까지의 시간은 브라우저 시계로 측정한다.

## 검증

```powershell
uv run ruff check .
uv run ruff format --check .
uv run lint-imports
uv run pytest -q
node --test tests/web/*.test.mjs
```

자동 테스트는 합성 이미지/가짜 모델과 브라우저 상태 로직을 검증한다. 실물 카메라 성능 검증은
별도로 시행한다. 정답 라벨을 직접 확인하고 정확 판독, 오독 확정, 확인 부족, 누락, 지연을 기록한다.
한 영상의 겹치는 구간은 독립된 현장 표본으로 취급하지 않는다. 10분 연속 운전 시 메모리와
대기열이 증가하지 않는지도 확인한다.

변경 범위는 SW의 입력 어댑터·묶음 처리·서버·화면이다. `schemas.py`, AI 선택 알고리즘,
단일 프레임 파이프라인은 이번 기능에서 변경하지 않았다. 의존성 및 CI 변경은 리뷰 때 별도 확인한다.

### 2026-10-26 개발 확인

- 실제 모델의 로딩 및 워밍업 후 `ready=true` 확인.
- 기존 1080p 사진 6장을 묶음 API에 전송: HTTP 200, 3장 시도 후 2개 결과 일치,
  서버 처리 약 3.32초(선택 약 1.06초, 판독 약 1.99초).
  이는 API 연결 시험이며 실시간 촬영·정답 검증·현장 성능 측정이 아니다.
- Windows의 `.mjs` MIME 및 브라우저 타이머 호출 문제를 실제 화면에서 확인하고 수정.
- 내장 브라우저의 카메라 권한 거부 상태를 확인. 실제 손 이동 및 10분 카메라 운전 시험은
  카메라 권한을 허용한 일반 브라우저에서 별도로 수행해야 한다.
- 사용자 제공 카메라 실험 이력 화면의 최근 10건: 확정 번호 없음, 처리 4.023~4.859초
  (평균 4.425초). 당시 이력은 실패 상태를 모두 '확인 필요'로 합쳤으므로 미검출·디코딩 실패·
  충돌 중 원인을 이 화면만으로 확정할 수 없다. 상태 구분 표시와 비식별 진단 로그를 보강했다.
- 추가 화면에서 3장 시도 중 1장 판독 성공(`provisional`), 대표 프레임의 1차 판독 성공을 확인.
  성공한 대표 프레임의 단계와 묶음 전체 교차 확인을 혼동시키던 '확인 필요' 및 고정 실패 문구를
  수정했다. 2장 일치 확정 기준은 그대로 유지한다.
- 표시 수정 검증: Python 250개 통과/10개 건너뜀, JavaScript 17개 통과. 별도 로컬
  화면에 가짜 묶음 응답을 넣어 실시간·이력·상세 표시와 성공/확인 부족/충돌 상태를 확인했다.
  이는 화면 회귀 검사이며 실물 카메라의 교차 확인 성공률 측정과는 별개다.
