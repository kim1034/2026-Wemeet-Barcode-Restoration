# AI파트가 할 일

**담당: 김시선, 김대원**
**내 폴더: `wemeet/ai/`**

---

## 한 문단 요약

사진에서 **바코드를 찾아 잘라내고**(1단계), **얼마나 휘었는지 예측합니다**(2단계). 잘라낸 결과와 휘어짐 정보를 SW파트에게 넘기면, SW파트가 OpenCV로 펴서 번호로 바꿉니다.

**우리는 이미지를 만들지 않습니다.** 곡률·주름을 숫자로 내놓을 뿐입니다.

우리는 **악기를 만드는 쪽**입니다. SW파트가 지휘자로서 우리 함수를 불러다 씁니다.

### 그래서 우리가 SW파트를 부르면 안 됩니다

헷갈리기 쉬운 지점이라 먼저 짚습니다. **데이터는 우리에게서 SW로 흐르지만, 부르는 방향은 반대입니다.**

```
데이터 흐름   사진 → 검출(우리) → 기하 추정(우리) → 보정(SW) → 디코딩(SW)
호출 방향     pipeline.py(SW) ──부른다──▶ detect() · estimate_geometry()(우리)
```

우리 함수가 먼저 실행되지만, **그 실행을 시작시키는 것은 SW파트의 `pipeline.py`** 입니다. 우리가 SW를 부르려고 하면 서로 부르는 원이 생겨 순환이 됩니다.

우리 코드는 **불리기만 하고 아무것도 시작하지 않습니다.** 대신 이런 이득이 있습니다 — `detect()` 를 파이프라인 없이 노트북에서 바로 부를 수 있습니다. 서버도 디코더도 필요 없습니다.

```python
from wemeet.ai.detection import detect
boxes = detect(image)      # 실험할 때 이게 편합니다
```

전체 호출 순서는 [구조와 규칙](../architecture.md#코드가-흐르는-순서)에 코드로 적어뒀습니다.

## 절대 하면 안 되는 것

```python
from wemeet.sw.decoding import decode      # ← 안 됩니다
from wemeet.data.synthesis import warp     # ← 안 됩니다
```

**우리 파일에 `wemeet.sw`나 `wemeet.data`라는 글자를 쓰지 않습니다.** 필요한 게 있으면 `wemeet.schemas`에서 가져옵니다.

```python
from wemeet.schemas import DetectedBarcode, GeometryField        # ← 이건 됩니다
```

**왜 그런가**: SW파트가 우리를 부릅니다. 우리가 SW파트를 부르면 서로 부르는 원이 생기고, 그러면 파이썬이 이런 에러를 냅니다.

```
ImportError: cannot import name 'DetectedBarcode' from partially initialized
module 'wemeet.sw.schemas' (most likely due to a circular import)
```

이 에러는 어느 파일을 먼저 실행하느냐에 따라 나타났다 사라집니다. 테스트는 통과하는데 서버만 안 뜨는 식이라 원인 찾기가 아주 어렵습니다.

걱정하지 않아도 됩니다. **실수로 쓰면 PR이 빨간 X로 막힙니다.** CI가 검사합니다.

## `wemeet/ai/detection/` — 1단계 탐지

### 무엇을 하는 파일인가

사진 한 장을 받아서 바코드가 있는 부분만 잘라냅니다. 비스듬히 놓인 바코드는 **똑바로 세워서** 잘라냅니다.

**이 프로젝트는 사진 한 장에 바코드가 하나만 있다고 가정합니다.** 그래서 리스트가 아니라 하나(또는 못 찾으면 `None`)만 반환합니다.

### 구현할 함수

```python
def detect(image_bgr: np.ndarray) -> DetectedBarcode | None:
```

| | 내용 |
|---|---|
| 입력 | BGR 이미지, 0~255, shape `(H, W, 3)`, dtype `uint8` |
| 출력 | `DetectedBarcode` 하나, 또는 못 찾으면 `None` |
| 못 찾으면 | `None` — **예외를 던지지 마세요** |

### 반환할 것

```python
from wemeet.schemas import DetectedBarcode

DetectedBarcode(
    crop_bgr_uint8 = crop,      # 잘라낸 이미지. BGR 순서, 0~255
    angle_deg_ccw  = 12.5,      # 몇 도 돌려서 세웠는지. 도(degree), 반시계
    confidence     = 0.93,      # 0.0 ~ 1.0
)
```

**이름에 붙은 단위를 반드시 지키세요.**

- `crop_bgr_uint8` — **BGR** 순서입니다. OpenCV는 BGR, PyTorch는 RGB입니다. 이거 헷갈리면 추정 결과가 이상하게 나오고, 원인 찾는 데 며칠 걸립니다
- `angle_deg_ccw` — **도(degree)**, **반시계** 방향입니다. 라디안 아닙니다

틀린 값을 넣으면 그 자리에서 바로 에러가 납니다. `schemas.py`가 검사합니다.

### 지켜야 할 것

- 잘라낸 이미지는 회전을 보정해서 **바코드가 수평**이 되게 합니다
- **110ms 안에** 끝냅니다 (전체 500ms 중 우리 몫)
- `wemeet.sw` / `wemeet.data` 를 import하지 않습니다

### 아직 안 정해진 것

**어떤 모델을 쓸지 미정입니다.** 후보 3개를 비교해서 정합니다 → [`docs/decisions/0002-탐지-모델-선정.md`](../decisions/0002-탐지-모델-선정.md)

| 후보 | 장점 | 단점 |
|---|---|---|
| **전통 영상처리** (MSER + 최소외접사각형) | 학습이 필요 없어서 며칠이면 됨 | 배경이 복잡하면 약함 |
| **Ultralytics YOLO-OBB** | 자료가 많고 회전 박스를 기본 지원 | 라이선스가 AGPL-3.0 |
| **YOLOX / MMRotate** | 라이선스 자유 | 설치·학습이 어려움 |

**9월 1주차에 전통 영상처리부터 만듭니다.** 학습이 필요 없어서 빠르고, 이게 기준선이 됩니다. 그다음 YOLO로 학습해서 비교합니다.

그리고 이 규칙을 미리 정해뒀습니다 — **전통 영상처리가 아래를 만족하면 YOLO 학습을 아예 건너뜁니다.**

- 탐지 누락률 5% 이하
- 크롭 각도 오차 5° 이하
- 추론 110ms 이하

건너뛰게 되면 학습·튜닝·라벨링이 전부 사라집니다. 11월 일정이 빡빡하니 이게 최선일 수도 있습니다. **"딥러닝이 필요 없었다"는 결과도 보고서에 쓸 가치가 있습니다.**

### 막히면 이렇게 시작하세요

`TODO` 자리에 이걸 넣으면 파이프라인이 일단 돌아갑니다. 이미지 중앙 40%를 그냥 자르는 가짜 구현입니다.

```python
def detect(image_bgr: np.ndarray) -> DetectedBarcode | None:
    h, w = image_bgr.shape[:2]
    crop = image_bgr[int(h * 0.3):int(h * 0.7), int(w * 0.3):int(w * 0.7)]
    return DetectedBarcode(
        crop_bgr_uint8=crop,
        angle_deg_ccw=0.0,
        confidence=0.5,
    )
```

가짜라도 넣어두면 전체가 돌아가고, 자기가 만든 게 어디에 쓰이는지 눈으로 볼 수 있습니다.

## `wemeet/ai/geometry/` — 2단계 기하 추정

### 무엇을 하는 파일인가

잘라낸 바코드를 받아서 **얼마나 휘었는지 예측합니다.** 이미지를 만들지 않습니다.

**이게 이 프로젝트에서 가장 자주 오해받는 부분입니다.** 우리는 구겨진 바코드를 "복원"하지 않습니다. 곡률·주름을 **숫자로** 내놓고, 실제로 펴는 것은 SW파트가 OpenCV로 합니다.

### 왜 이미지를 만들지 않나

생성 모델이 만든 가짜 바코드는 **체크섬을 우연히 통과할 수 있습니다.** Code128은 약 1/103, EAN-13은 1/10입니다. 세관에서 하루 수천 건이면 **틀린 번호가 조용히 통과하는 사고**가 실제로 납니다. 못 읽으면 사람이 처리하지만, 틀리게 읽으면 화물이 엉뚱한 곳으로 갑니다.

그래서 우리 반환형에는 **이미지 필드가 아예 없습니다.** 실수로라도 픽셀을 만들어 넘길 수 없습니다.

부수 효과로 우리 일이 쉬워집니다 — 학습 데이터를 **합성으로 무한정 만들 수 있습니다.** 깨끗한 바코드에 알고 있는 왜곡을 입히면 정답이 곧 그 역함수입니다. 라벨링이 필요 없습니다.

### 구현할 함수

```python
def estimate_geometry(target: DetectedBarcode) -> GeometryField:
```

| | 내용 |
|---|---|
| 입력 | `DetectedBarcode` **하나** (리스트 아님) |
| 출력 | `GeometryField` — 제어점 좌표 몇십 개. 이미지가 아닙니다 |

리스트가 아니라 하나만 받습니다 — `detect()`도 하나만 반환하므로 자연스럽게 이어집니다.

### 입력은 이미지입니다 — 출력만 숫자입니다

헷갈리기 쉬운 지점입니다. **이미지를 읽는 것은 괜찮고, 이미지를 만드는 것이 위험한 것**입니다.

```
입력   target.crop_bgr_uint8      이미지 (BGR, uint8, (H, W, 3))
         ↓  CNN 백본 + spatial 좌표 회귀 헤드
출력   control_points             src 좌표 96개 (48점 × 2좌표)
```

원본 사진 전체가 아니라 **1단계에서 잘라낸 크롭**을 받습니다. 모델 구조로 보면 흔한 **이미지 입력 → 좌표 회귀**입니다. 세그멘테이션 헤드나 생성 디코더가 없어서 훨씬 가볍습니다.

### 리사이즈해도 좌표는 안 어긋납니다

크롭은 **매번 크기가 다릅니다.** 바코드가 크게 찍히면 800×600, 작게 찍히면 200×150입니다. CNN에 넣으려면 고정 크기(현재 v1 제안: `H=160, W=384`)로 리사이즈해야 합니다.

**그래도 됩니다.** 정규화 좌표는 리사이즈에 불변입니다.

```
crop 400×300  →  resize 160×384  →  모델  →  (0.62, 0.41)
crop 800×600  →  resize 160×384  →  모델  →  (0.62, 0.41)    같은 값

SW파트가 원래 크롭 크기를 곱해서 픽셀로 되돌립니다
  400×300 이면 (248, 123)      800×600 이면 (497, 246)
```

계약을 픽셀로 정했다면 "입력이 256인데 원본은 800이었으니 3.1배"라는 정보를 같이 넘겨야 했고, 그게 빠지는 순간 사고가 났을 겁니다. **정규화가 그 문제를 없앤 것**입니다.

### 함정 — letterbox 패딩

바코드는 가로로 깁니다(예: 400×100). 정사각형에 맞추는 방법이 두 가지인데 **결과가 다릅니다.**

| 방법 | 정규화 좌표 | 주의 |
|---|---|---|
| **강제 리사이즈** (종횡비 무시) | 그대로 맞습니다 | 세로로 늘어나지만 학습·추론에서 일관되면 문제없습니다 |
| **letterbox** (위아래 패딩) | **어긋납니다** | 모델이 내는 좌표가 "패딩된 이미지" 기준이 됩니다 |

letterbox를 쓰면 **패딩을 뺀 원본 크롭 기준으로 환산해서** 넘겨야 합니다. 안 하면 위아래로 밀린 채 펴지고, **약한 왜곡에서는 또 우연히 읽혀서 늦게 발견됩니다.**

계약이 이걸 일부 막아줍니다 — `dst` 제어점이 0~1을 벗어나면 그 자리에서 `AssertionError`가 납니다. 픽셀 좌표를 넣는 실수도 잡힙니다.

어느 방법을 쓸지는 `decisions/0003`에서 정합니다.

### 채널은 줄여도 됩니다

계약은 BGR 3채널을 주지만, 바코드는 **색 정보가 무의미**합니다. v1 제안은 모델
내부에서 grayscale으로 변환한 뒤 3채널로 repeat하는 것입니다. ImageNet pretrained
백본의 첫 convolution을 그대로 사용할 수 있고, 계약을 바꾸지 않습니다.

```python
gray = cv2.cvtColor(target.crop_bgr_uint8, cv2.COLOR_BGR2GRAY)   # 모델 안에서
```

### 반환할 것

```python
from wemeet.schemas import GeometryField

GeometryField(
    control_points_dst_norm = dst,     # (N, 2) 펴진 격자 위치. 보통 규칙적인 격자
    control_points_src_norm = src,      # (N, 2) 그 내용이 "지금" 있는 위치
    method                  = "tps",    # "tps" 만 허용
    confidence              = 0.82,     # 0.0 ~ 1.0
)
```

**좌표 규칙을 반드시 지키세요.** 이걸 틀리면 SW파트가 이미지를 거꾸로 폅니다.

| 항목 | 규칙 |
|---|---|
| 기준 | `target.crop_bgr_uint8` 입니다. **원본 이미지가 아닙니다** |
| 단위 | **0.0~1.0 정규화**입니다. 픽셀이 아닙니다 |
| 순서 | `(x, y)` 입니다 |
| 방향 | `dst` = 펴진 격자, `src` = 지금 있는 위치 |

**방향을 뒤집으면 왜곡이 두 번 적용됩니다.** 그런데 약한 왜곡에서는 우연히 읽히기도 해서 버그를 놓치기 쉽습니다 — 사전 실험에서 실제로 겪었습니다. 결과가 들쭉날쭉하면 방향을 먼저 의심하세요.

### 지켜야 할 것

- **150ms 안에** 끝냅니다 (전체 500ms 중 우리 몫)
- 제어점은 확정된 **`16×3=48점`**을 사용합니다. 모델이 예측하는 `src` 좌표는 96개이고, `dst`는 regular 격자로 생성합니다
- 출력은 좌표 96개지만 spatial feature가 필요한 문제입니다. v1 구현 기준 백본은 `ResNet18-C3`이며, `MobileNetV3-Small`·`EfficientNet-B0`와 같은 Head로 비교합니다

### 정확도는 비교 지표로 측정합니다

예전 5.5px 모듈 폭·무노이즈 조건의 표를 일반적인 성능처럼 사용하지 않습니다.
현재 제어점 실험은 `src`에 pixel 단위 가상 오차 sigma를 넣어 `16×3` 격자의
좌표 오차와 보정 후 판독률을 함께 측정했습니다. 실제 모델의 sigma는 학습 후
합성 validation set에서 측정해야 합니다.

초기 비교에서는 원본 crop pixel 기준 mean error, RMSE, P95를 기록하고,
약 2px 수준의 effective error 영역을 중요한 관찰 기준으로 봅니다. 이것은
보장된 목표 성능이 아닙니다. 모듈 폭·블러·노이즈·반사에 따라 결과가 달라지므로
합성 결과를 실촬영 성능으로 그대로 옮기지 않습니다.

### 되살릴 수 없는 한계

합성 스파이크에서는 정보가 사라지는 경계가 약 0.8px 모듈 폭까지 관찰됐지만,
이는 무노이즈 조건의 상한입니다. 모듈이 지나치게 압축되거나 반사로 정보가
소실된 경우에는 어떤 geometry prediction도 없는 픽셀을 복원할 수 없습니다.
이 경우 억지로 그럴듯한 값을 내지 말고, `confidence`와 pipeline 정책으로
실패를 안전하게 처리해야 합니다.

| 후보 | 출력 | 장점 | 위험 |
|---|---|---|---|
| **제어점 회귀 + TPS** | **48점 × 2 = 96개 좌표** | 매끄러움이 보장돼 **픽셀이 찢어지지 않음**. 학습이 쉬움 | 급격한 주름에 한계 |
| Dense flow map | (H, W, 2) | 주름까지 표현 | 정규화 필요. 노이즈 시 찢어짐 |
| 4점 호모그래피 | 8개 숫자 | 가장 단순. **베이스라인으로 반드시 측정** | 평면 왜곡만 |

**제어점 회귀부터 합니다.** `ResNet18-C3`를 v1 구현 기준으로 삼고,
`MobileNetV3-Small`·`EfficientNet-B0`를 동일 조건에서 비교합니다. 최종 배포 백본은
비교 실험 후 재확인합니다. 상세 계획은 [Stage 2 백본 비교 설계](../experiments/2026-09-15-stage2-backbone/README.md)를 보세요.

### 손실 함수

제어점 좌표 회귀이므로 단순합니다.

| 항목 | 역할 |
|---|---|
| **L1 / Smooth L1** | 제어점 좌표 오차. 이것만으로 시작해도 됩니다 |
| (선택) 재투영 손실 | 추정한 필드로 실제로 펴서 정답 이미지와 비교 |

기존 복원 방식에서 필요했던 SSIM·엣지 손실이 **필요 없습니다.** 이미지를 만들지 않으니까요. 학습이 훨씬 단순해집니다.

### 막히면 이렇게 시작하세요

**항등 필드**를 내놓는 가짜 구현입니다. "휘지 않았다"고 답하는 것이라 파이프라인이 그대로 돌아갑니다.

```python
import numpy as np

from wemeet.schemas import DetectedBarcode, GeometryField


def estimate_geometry(target: DetectedBarcode) -> GeometryField:
    xs = np.linspace(0.0, 1.0, 16)
    ys = np.linspace(0.0, 1.0, 3)
    gx, gy = np.meshgrid(xs, ys)
    grid = np.stack([gx.ravel(), gy.ravel()], axis=1)      # 16x3 = 48점
    return GeometryField(
        control_points_dst_norm=grid,
        control_points_src_norm=grid,      # src == dst 이므로 아무것도 안 움직인다
        method="tps",
        confidence=0.1,                     # 낮게 — 추정한 게 아니라는 표시
    )
```

이 가짜 구현이 **기준선**입니다. 우리 모델이 이것보다 못하면 의미가 없습니다. 그리고 4점 호모그래피 베이스라인도 반드시 측정해서, 우리 모델이 그보다 나은지 확인하세요.

## 학습할 때 (`train_detection.py` / `train_geometry.py`)

### 파일을 두 개로 나눈 이유

검출과 기하 추정은 학습 방식이 완전히 다릅니다. 검출은 Ultralytics API를 부르고, 기하 추정은 커스텀 PyTorch 루프(좌표 회귀)를 돌립니다. 한 파일에 넣으면 금방 수백 줄이 되고, 둘이서 같은 파일을 고쳐 충돌합니다.

### 학습 기록은 W&B에

상세는 [W&B 사용법](../external/wandb.md)에 있고, 핵심만 적으면 이렇습니다.

```python
import wandb

wandb.init(
    project="wemeet-barcode",
    entity="metro-wemeet",
    name="detection-yolo-obb-v2",        # <단계>-<모델>-v<번호>
    tags=["candidate"],
    config={
        "dataset_revision": "synth-v1",   # ← 이게 제일 중요합니다
        "seed": 42,                       # ← 이것도
        "model": "yolov8n-obb",
        "epochs": 100,
        "lr": 0.001,
    },
)
```

**`dataset_revision`을 반드시 남기세요.** 데이터가 계속 늘어나는 프로젝트입니다. 이걸 안 남기면 두 실험의 성능 차이가 데이터 때문인지 설정 때문인지 알 수 없습니다.

기록할 지표는 정확도만이 아닙니다.

```python
wandb.summary.update({
    "mAP50": 0.912,
    "mAP50_95": 0.624,
    "angle_error_deg": 2.4,          # OBB는 각도가 크롭 품질을 좌우합니다
    "inference_ms_p50": 38.4,        # 110ms 예산 확인
    "inference_ms_p95": 51.2,
})
```

**추론 시간을 꼭 재세요.** 정확해도 예산을 넘으면 탈락입니다.

### 실패한 실험도 남깁니다

`failed` 태그를 붙여서 남겨두세요. 지우면 다른 사람이 같은 실수를 반복합니다. "학습률 0.1은 발산한다"도 정보입니다.

## 자주 헷갈리는 것

**Q. `schemas.py`를 고쳐야 할 것 같은데요?**
혼자 고치지 마세요. SW파트 승인이 있어야 머지됩니다. Issue를 만들고 `decision` 라벨을 붙여서 상의하세요. 이 파일이 우리와 SW파트를 잇는 유일한 약속입니다.

**Q. 사진 한 장에 바코드가 여러 개 찍히면 어떻게 하죠?**
지금 계약은 한 장에 하나만 있다고 가정합니다. 실제로 여러 개가 흔하다면 `schemas.py`를 고치는 논의가 필요하니, 혼자 처리하지 말고 Issue로 SW파트와 상의하세요.

**Q. 기하 추정이 실패하면 예외를 던져야 하나요?**
아니요. 파이프라인이 알아서 처리합니다. 예외를 던지면 SW파트가 잡아서 원본 크롭으로 대체합니다.

**Q. BGR인지 RGB인지 자꾸 헷갈립니다.**
변수 이름에 적혀 있습니다. `crop_bgr_uint8`은 BGR, `image_gray_uint8`은 흑백입니다. 이름을 믿으세요.
