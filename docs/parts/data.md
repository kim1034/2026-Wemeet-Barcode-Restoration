# 데이터파트가 할 일

**담당: 김강민, 조아라**
**라벨링 참여: 이다현, 이아침 (1학년)**
**내 폴더: `wemeet/data/`**

---

## 한 문단 요약

AI 모델이 **배울 데이터를 만듭니다.** 오픈소스 데이터를 받아오고, 깨끗한 바코드에 인위적으로 훼손을 입혀서 "훼손된 것 ↔ 정답" 짝을 대량으로 만들고, 실제로 촬영해서 최종 평가용 데이터를 준비합니다.

**이 파트가 프로젝트의 상한선을 정합니다.** 모델이 아무리 좋아도 데이터가 현장과 다르면 성능이 안 나옵니다.

## 우리가 쓸 수 있는 것

```python
from wemeet.schemas import DecodeResult              # ← 됩니다
from wemeet.sw.decoding import decode                # ← 됩니다 (정답 확보용)
from wemeet.ai.detection import detect                # ← 안 됩니다
from wemeet.sw.pipeline import run                    # ← 안 됩니다
```

`sw.decoding`만 예외로 허용됩니다. 촬영한 사진에서 정답 번호를 읽어내려면 디코더가 필요하기 때문입니다. 그 외에는 다른 파트를 부르지 않습니다.

## 0단계. 심볼로지 확정 (9월 1주차, 최우선)

**실제 인천세관 송장의 바코드가 무슨 종류인지 확인합니다.** Code128인지, ITF-14인지, GS1-128인지.

멘토에게 묻거나 현장 사진을 봐야 합니다. 팀장이 확인하지만 우리가 결과를 받아야 다음 단계로 갑니다.

### 왜 이게 최우선인가

이걸 모르면 아래가 전부 정해지지 않습니다.

- 오픈소스 데이터에서 **무엇을 걸러낼지**
- 합성할 때 **무슨 바코드를 그릴지**
- 평가 대상이 무엇인지

**틀린 종류로 수만 장을 만들어놓고 나중에 알게 되면 그 시간이 전부 사라집니다.**

### QR은 범위 밖일 가능성이 높습니다

우리가 쓸 오픈소스 데이터에 QR이 섞여 있습니다. 그런데 이 프로젝트의 문제 정의는 전부 1D 바코드 논리입니다 — 바 간격 비율, 흑백 명암비, 평탄화.

QR은 **오류정정이 내장**되어 있어서 훼손 내구성이 근본적으로 다릅니다. 그리고 QR에는 1D 바코드의 바 높이 방향 정보 중복이 없어서 **반사 대응 기법을 쓸 수 없습니다.** 한 모델로 둘 다 하면 양쪽 다 애매해집니다.

**1D 우선, QR은 범위 외**로 정하는 게 좋다고 판단하고 있습니다. 현장이 실제로 QR을 쓰지 않는다면 확정합니다.

기록: [`docs/decisions/0001-바코드-심볼로지-범위.md`](../decisions/0001-바코드-심볼로지-범위.md)

## 3단계. 라벨링 (9월 2주차) — 1학년 참여

### 얼마나 하나

1단계 결과로 OBB 재라벨링이 필요하다고 나오면, **952장 ÷ 4명 = 1인당 238장**입니다.

HBB에서 OBB로는 자동 변환이 안 됩니다. 회전 각도를 사람이 다시 표시해야 합니다.

### 도구는 CVAT

`labelImg`는 **회전 박스를 지원하지 않아서** 쓸 수 없습니다.

| 도구 | 비고 |
|---|---|
| **CVAT** (권장) | 회전 박스 지원. 여러 명 동시 작업과 검수 기능 있음. 무료 |
| Roboflow | 더 쉽지만 무료 플랜 용량 제한 |

설정 절차는 [코드 밖에서 해야 하는 일 §4](../external/README.md#4-cvat--라벨링-도구)에 있습니다.

### 시작하기 전에 가이드라인을 만드세요

**4명이 각자 판단하면 라벨이 일관되지 않고, 그러면 mAP 목표 달성이 불가능합니다.** 최소한 이 셋을 정해서 문서 1장으로 공유합니다.

1. 바코드의 **어디까지를 박스에 넣는가** — 좌우 여백(quiet zone)을 포함하는지
2. **부분적으로 가려진 바코드**는 라벨링하는지, 건너뛰는지
3. **각도 기준선을 어디로 두는가** — 바가 수직인 방향인지 수평인 방향인지

**3번이 특히 중요합니다.** 기준이 어긋나면 크롭이 90° 돌아간 상태로 학습되고, 그러면 디코더가 전혀 읽지 못합니다.

### 품질 관리 3단계

| 단계 | 무엇 |
|---|---|
| **공동 작업 20장** | 처음 20장은 4명이 같은 이미지를 라벨링하고 결과를 비교. 기준이 어긋나는 지점을 여기서 잡습니다 |
| **교차 검수 10%** | 각자 작업분의 10%를 다른 사람이 확인 |
| **3학년 표본 검수** | 최종 확인 |

**불일치율을 `decisions/0004`에 기록하세요.** 나중에 mAP가 낮게 나올 때 원인이 모델인지 라벨인지 판단할 수 있는 유일한 근거입니다. 이게 없으면 AI파트가 몇 주를 헤맵니다.

### 1학년에게

라벨링은 단순 반복 작업처럼 보이지만 **이 프로젝트에서 가장 영향력이 큰 작업 중 하나**입니다. 라벨이 정확하면 모델이 잘 배우고, 어긋나면 모델이 아무리 좋아도 성능이 안 나옵니다.

애매한 이미지가 나오면 혼자 판단하지 말고 물어보세요. 20장 공동 작업이 그걸 위한 시간입니다.

## 4단계. 합성 데이터 만들기 (9월 2~3주차)

### 무엇을 하나

깨끗한 바코드에 **인위적으로 훼손을 입혀서** "훼손된 것 ↔ 정답" 짝을 만듭니다. 이걸 **역방향 합성**이라고 합니다.

```
깨끗한 바코드
      ↓  왜곡 파라미터를 뽑아서 cv2.remap 으로 적용
훼손된 바코드 (입력)  +  왜곡의 역함수 = 정답 제어점

→ 세 가지를 저장합니다: 훼손 이미지 · 정답 제어점 · 정답 번호
```

**우리 일이 크게 쉬워졌습니다 (2026-08-04).** 예전에는 "훼손된 것 ↔ 펴진 것" 이미지 쌍을 만들어야 했는데, 이제 **정답이 우리가 넣은 왜곡 파라미터 그 자체**입니다. 라벨링이 필요 없고 픽셀 정렬 걱정도 없습니다.

이유는 AI가 이미지를 만들지 않게 바뀌었기 때문입니다. AI는 "얼마나 휘었는지"만 예측하고 실제로 펴는 것은 OpenCV가 합니다. 그래서 우리는 **"얼마나 휘게 했는지"를 정답으로 주면 됩니다.**

수백 장짜리 실측만으로는 부족하니, 이 방법으로 **수만 장**을 만듭니다.

### 원본 재료를 직접 그립니다 — 기획서와 다릅니다

기획서는 Hugging Face의 `barcodes-google-ocr`을 원본 재료로 쓰라고 했습니다. **그런데 확인해보니 그러면 안 됩니다.**

그 데이터는 416px 실사 촬영본이고, 스키마가 `pixel_values` / `label`(1 class) / `ocr`입니다. 즉 정답 바코드 번호가 보장된 필드가 아니고, **이미지도 이미 흐릿합니다.**

**열화된 원본에 왜곡을 덧씌우면 정답 제어점이 가리키는 위치가 실제와 어긋납니다.** 이미 흐릿한 이미지에서는 "원래 이 바가 어디 있었는지"가 불분명해집니다.

그래서 `python-barcode` 또는 `treepoem`으로 **직접 렌더링합니다.**

```python
import barcode
from barcode.writer import ImageWriter

code = barcode.get("code128", "8801234567890", writer=ImageWriter())
code.save("clean")     # 픽셀이 완벽한 원본. 정답 번호도 우리가 아는 값
```

이렇게 하면 **정답 번호를 아는 깨끗한 이미지를 무한히** 만들 수 있습니다. HF 데이터는 원본 재료가 아니라 **탐지 모델 학습용**으로 씁니다.

### 훼손 입히기

기획서 4.2.2대로 두 종류를 섞습니다.

| 훼손 | 방법 | 정답을 알 수 있나 |
|---|---|---|
| **비닐 주름·곡률** | `cv2.remap` 으로 직접 적용 (원통 곡률 + 국소 주름) | **예 — 역함수가 정답** |
| **빛 반사** | 인위적 광원(Glare/Flare) 효과 | 제어점과 무관 |

두 훼손이 **섞인** 데이터로 학습시켜야 합니다. 현장에서는 둘이 같이 발생하니까요.

### 왜 Albumentations 대신 cv2.remap 인가

`GridDistortion` / `ElasticTransform` 은 왜곡을 걸어주지만 **적용한 변환을 돌려주지 않습니다.** 우리는 그 변환이 곧 정답이므로 직접 알아야 합니다.

`cv2.remap` 을 쓰면 우리가 매핑을 만들었으니 정답을 그대로 저장할 수 있습니다.

```python
# 예: 원통에 감긴 효과. col[x] = 출력 열 x 가 원본의 어느 열에서 왔는지
theta = np.deg2rad(각도)
c = (w - 1) / 2
r = c / theta
u = r * np.arcsin(np.clip((np.arange(w) - c) / (r * np.sin(theta)) * np.sin(theta), -1, 1))
col = (u + c).astype(np.float32)
```

### 정답 제어점을 만들 때 방향을 뒤집지 마세요

**가장 흔한 실수이고, 약한 왜곡에서는 우연히 맞아 보여서 놓치기 쉽습니다.** 사전 실험에서 실제로 겪었습니다.

```python
# 틀림 — 이건 "펴진 -> 휜" 방향입니다
src_x = np.interp(dst_x, np.arange(w), col)

# 맞음 — 역함수를 써야 "휜 -> 펴진" 이 됩니다
src_x = np.interp(dst_x, col, np.arange(w, dtype=np.float64))
```

만든 데이터가 맞는지 확인하는 방법: **정답 제어점으로 직접 펴서 디코더에 넣어보세요.** 읽히면 맞고, 안 읽히면 방향이나 좌표계가 틀렸습니다. 이게 가장 싼 검증입니다.

### 어느 각도까지 왜곡할지

사전 실험(설계 문서 §8.4)에서 한계를 측정했습니다.

| 가로 압축 | 가장자리 모듈 폭 | 판정 |
|---|---|---|
| 70° | 1.9 px | 보정하면 읽힘 |
| 84° | 0.6 px | **불가 — 정보 소실** |

**모듈이 1px 이하가 되는 왜곡은 학습에 넣어도 모델이 배울 수 없습니다.** 정보가 없는 것을 맞추라고 하는 셈입니다. 왜곡 범위 상한을 여기 맞춰 정하세요.

### 조심할 것 — 전처리로 미리 펴지 마세요

기획서 4.1.1에 "명암비 조절 및 **기하학적 평탄화** 전처리를 수행한다"고 적혀 있는데, 이 문장은 개념이 뒤집혀 있습니다.

**평탄화는 파이프라인 3단계(SW파트의 기하 보정)가 하는 일입니다.** 우리가 전처리로 미리 펴버리면 2단계 모델이 배울 게 없어지고, 3단계가 할 일도 없어집니다.

우리가 하는 건 정답 쪽을 규격에 맞게 정리하는 것(크기 통일 등)까지입니다.

### 시드를 고정하세요

```python
import random, numpy as np
random.seed(42)
np.random.seed(42)
```

**데이터가 매번 달라지면 모델 비교가 성립하지 않습니다.** AI파트가 두 모델을 비교할 때 데이터가 다르면 무엇 때문에 성능이 달라졌는지 알 수 없습니다.

### 버전을 나눠서 올립니다

```
synthetic/v1/     ← 덮어쓰지 않습니다
synthetic/v2/
```

폴더를 나누고 Hugging Face에 태그를 붙입니다. 덮어쓰면 이전 실험을 재현할 수 없습니다. 상세는 [Hugging Face 사용법](../external/huggingface.md).

## 5단계. 실촬영 (9월 3~4주차) — 순서가 절대적입니다

### 이 순서를 반드시 지키세요

```
① 송장을 평탄한 상태로 촬영  →  디코더로 정상 판독  →  정답 번호 기록
                    ↓
② 같은 송장을 구기고 비닐 씌우고 반사 유도  →  재촬영
                    ↓
③ 두 이미지를 같은 ID로 짝지어 저장
```

**순서를 바꾸면 구겨진 사진의 정답을 알 방법이 없어서 데이터가 무효가 됩니다.** 구겨진 사진만 있으면 정답이 뭔지 확인할 수 없습니다. 사람이 눈으로 읽어서 입력하는 것도 오타 위험이 있어서 신뢰할 수 없습니다.

①의 자동화 코드가 `wemeet/data/ground_truth.py`입니다. 이 파일이 `sw.decoding`을 부르는 유일한 우리 코드입니다.

### 기록 시트

```csv
id,ground_truth,symbology,damage_type,damage_level,lighting,note
F0001,8801234567890,CODE128,curvature,high,indoor_led,비닐 2겹
F0002,8801234567891,CODE128,glare,mid,indoor_led,
```

`ground_truth`가 이 파일의 존재 이유입니다. ①에서 채워 넣습니다.

### 개인정보 — 이건 선택이 아닙니다

**실제 송장에는 수취인 이름·주소·연락처가 인쇄되어 있습니다.**

- **촬영 전에** 해당 영역을 불투명 테이프로 가립니다. 촬영 후 블러보다 확실합니다
- 촬영 원본은 **public 저장소에 절대 올리지 않습니다**
- **private** Hugging Face 저장소(`barcode-field`)에만 보관합니다

이 프로젝트가 송장 개인정보를 이렇게 신경 쓰는데 우리가 유출하면 안 됩니다.

### `dev` / `eval` 로 나눠서 촬영합니다

**촬영 시점부터 송장을 두 무더기로 갈라놓고 시작합니다.**

| 분할 | 비율 | 용도 | 여는 시점 |
|---|---|---|---|
| `dev` | 40% | 중간 점검, 디버깅 | 언제든 |
| `eval` | 60% | **최종 평가 전용** | **11월 2주차에 딱 한 번** |

**같은 송장의 다른 각도 사진이 양쪽에 들어가면 안 됩니다.** 사실상 유출입니다. 사진 단위가 아니라 **송장 단위**로 나눕니다.

`eval`은 어떤 경우에도 학습이나 튜닝에 노출되지 않습니다. 미리 보면 그 결과를 보고 조정하게 되고, 그 순간 "독립 평가 데이터"라는 성질이 사라집니다. 그러면 11월 최종 평가 숫자를 믿을 수 없게 됩니다.

준비물과 촬영 환경은 [코드 밖에서 해야 하는 일 §6](../external/README.md#6-촬영-준비-물리-작업)에 있습니다.

## 우리가 만드는 데이터가 왜 중요한가

이 프로젝트의 **가장 큰 위험**은 이겁니다.

> 합성 데이터로 학습한 모델이 **실제 비닐 반사와 3D 곡률에서는 안 통하는 것**

우리가 만드는 합성 훼손이 현장과 비슷할수록 이 위험이 줄어듭니다. 그래서 `GridDistortion` 파라미터를 대충 정하지 말고, **실촬영 사진과 비교해가며** 조정해야 합니다.

5단계 `dev` 분할이 그 비교 기준입니다. 합성 데이터에서의 성능과 `dev`에서의 성능 차이가 크면 합성 파라미터를 다시 조정합니다.

## 자주 헷갈리는 것

**Q. 이미지 파일을 git에 올려도 되나요?**
안 됩니다. `.gitignore`가 막고 있습니다. Hugging Face에 올리세요.

**Q. 합성 데이터를 몇 장 만들어야 하나요?**
기획서 산출물 기준은 최소 1,000장이지만, 실제 계획은 역방향 합성으로 **수만 장**입니다. 정확한 수는 학습해보고 정합니다 — AI파트와 상의하세요.

**Q. 실촬영 데이터를 학습에 써도 되나요?**
`dev`는 됩니다 (도메인 갭이 클 때). `eval`은 절대 안 됩니다.

**Q. 정답 번호를 눈으로 읽어서 입력하면 안 되나요?**
오타 위험 때문에 안 됩니다. 반드시 평탄 상태에서 디코더로 읽어서 기록하세요.

**Q. `sw.decoding` 말고 다른 파트 코드를 쓰고 싶은데요?**
CI가 막습니다. 정말 필요하면 Issue를 만들어 상의하세요 — 대개는 다른 방법이 있습니다.
