# 3단계(기하 보정) 구현 가이드

**누가 읽나**: SW파트 (`wemeet/sw/rectify.py` 담당)
**한 줄로**: 펴는 코드는 이미 돌아가고 있습니다. **옮겨오고, 골든 픽스처로 맞는지 확인하면 됩니다.**

짝이 되는 문서: [2단계 → 3단계 인계 규격](stage2-handoff.md) — **계약은 그쪽이 정본입니다.**
이 문서는 계약을 다시 적지 않고, 그 계약을 **어떻게 구현하고 무엇으로 검증하는가**만 답합니다.

> **왜 지금 이 문서가 생겼나**: 2026-09-15 에 합성 평가 세트 1,500장이 완성됐습니다.
> 정답 번호와 정답 제어점이 같이 들어 있어서, **3단계 구현이 맞는지 기계적으로 채점할 수
> 있게 됐습니다.** 그 전에는 "펴 보고 읽히면 맞겠지" 말고는 확인할 방법이 없었습니다.

## 1. `dst` 는 예측값이 아니라 상수입니다

`schemas.py` 는 `control_points_dst_norm` 을 "보통 규칙적인 격자" 라고만 적었는데,
**실제로는 항상 정확히 같은 48점입니다.** 평가 세트 1,500장의 `dst_norm` 을 전수
비교해 확인했습니다 — 최대 차이 `2.2e-16` (부동소수점 반올림).

```python
import numpy as np

N_X, N_Y = 16, 3                       # wemeet/data/synthesis.py:40
DST_NORM = np.array([[x, y]
                     for y in np.linspace(0.0, 1.0, N_Y)     # 행: 0.0, 0.5, 1.0
                     for x in np.linspace(0.0, 1.0, N_X)])   # 열: 0, 1/15, ... , 1
assert DST_NORM.shape == (48, 2)
```

배열 순서는 **행 우선**입니다 — 위쪽 줄 16개, 가운데 줄 16개, 아래쪽 줄 16개.

구조적으로도 보장됩니다. 제어점 생성부가 크롭 범위 `u_lo`/`u_hi` 를 이렇게 상쇄합니다:

```python
span = max(u_hi - u_lo, 1e-9)
dst.append([(u - u_lo) / span, v])     # u 가 linspace(u_lo, u_hi) 이므로 항상 0 → 1
```

**그래서 2단계 모델이 예측하는 것은 `src_norm` 96개 숫자(48점 × 2축)뿐입니다.**
`dst_norm` 은 학습 대상도, 전송해야 할 정보도 아닙니다. 계약이 그대로 실어 보내는 것은
호환성 때문이고, 3단계는 위 상수를 직접 만들어 써도 결과가 같습니다.

> 다만 **받은 `dst_norm` 을 무시하지는 마세요.** 지금은 상수지만 계약은 `(N, 2)` 로
> 열려 있습니다.

## 2. 참조 구현 — 이 코드가 30,000장의 라벨을 만들었습니다

`scripts/label_recipes.py` 의 `tps_flow` 와 `rectify` 입니다. 학습·평가 세트의 구간
라벨(`target` / `hard`)이 **전부 이 코드의 판정 결과**이므로, 3단계가 이것과 다르게
동작하면 데이터셋의 난이도 라벨이 3단계에 대해 의미를 잃습니다.

```python
def rectify(obs, dst_norm, src_norm, out_shape):
    ho, wo = out_shape
    hi, wi = obs.shape
    dst_px = dst_norm * np.array([wo - 1, ho - 1])     # 출력 기준
    src_px = src_norm * np.array([wi - 1, hi - 1])     # 입력 크롭 기준
    mx, my = tps_flow(src_px, dst_px, out_shape)
    return cv2.remap(obs, mx, my, cv2.INTER_CUBIC, borderMode=cv2.BORDER_REPLICATE)
```

`tps_flow` 전문은 같은 파일에 있습니다. **격자 축소가 들어 있지 않습니다** — 오프라인
라벨링 도구라 속도를 신경 쓰지 않았습니다. 3단계는 [축소를 넣어야 합니다](#5-격자-축소).

옮길 때 틀리기 쉬운 것 셋:

| | |
|---|---|
| `w - 1`, `h - 1` | `w`, `h` 가 아닙니다. `1.0` 은 마지막 픽셀 **중심**입니다 |
| `dst_px` 와 `src_px` 를 `tps_flow` 에 넣는 순서 | `tps_flow(src_px, dst_px, ...)` 입니다. 바꾸면 왜곡이 두 번 걸립니다 |
| `BORDER_REPLICATE` | `src` 는 크롭 밖(`-0.5 ~ 1.5`)을 가리킬 수 있습니다. 기본값(검정 채움)이면 그 영역이 막대로 읽힙니다 |

방향을 뒤집으면 **약한 왜곡에서는 우연히 읽혀서** 테스트를 통과합니다.
아래 골든 픽스처는 세 버킷 전부를 쓰므로 이걸 잡습니다.

## 3. 출력 캔버스 크기 (`out_shape`) — 여기가 제일 중요합니다

> **⚠️ [stage2-handoff.md](stage2-handoff.md) 의 「크롭과 같은 크기」를 그대로 따르지 마세요.**
> 그 문장은 「확대 검토했으나 확대 없이 0.8px 까지 복원되므로 우선순위 낮음」이라는
> 근거로 적힌 것인데, 평가 세트 1,500장으로 재보니 **24.5%p 를 잃습니다.**

`out_shape` 는 단순한 캔버스 크기가 **아닙니다.** TPS 커널 `r² log r²` 은 스케일
불변이 아니라, 굽힘 에너지가 `dst_px` 의 **절대 크기에 의존**합니다. 즉 `out_shape`
를 바꾸면 제어점 사이의 **보간 자체가 달라집니다.**

### 측정 (평가 세트 전수, n=1,500)

| `out_shape` | 번호 일치 |
|---|---|
| 정답 `(h_flat, w_flat)` | **1500/1500 (100.00%)** |
| 정답 폭 + 크롭 높이 | 1368/1500 (91.20%) |
| 크롭과 같은 크기 | 1132/1500 (**75.47%**) |
| 크롭 폭 + 종횡비 2.15 | 1110/1500 (74.00%) |

**폭이 지배적입니다.** 폭만 맞춰도 91.2% 인데 폭이 틀리면 75% 입니다. 크롭 폭은
펴진 폭과 버킷마다 다른 방향으로 어긋납니다 — `w_obs/w_flat` 중앙값이 `low` 1.049 /
`mid` 0.923 / `high` 0.787 이고(평가 세트 전수, 버킷당 500장), `low` 는 **69.8% 가
`w_flat` 보다 넓습니다**(여백 증강이 최대 +15% 를 붙이기 때문입니다). 감겨서 좁아지는
쪽이 이기는 것은 `mid`(넓은 것 25.2%)·`high`(5.0%) 이고, 최소는 0.404 까지 내려갑니다.
어느 쪽이든 크롭 폭을 쓰면 모듈을 틀린 배율로 재표본화하게 되고, 부족 표본화되는
`high` 에서 특히 손해가 큽니다.

### 추론 시점에는 `w_flat` 을 모릅니다

크롭 폭의 배수로 키워봤습니다 (n=300, 버킷당 100).

| 배율 | 1.0 | 1.5 | 2.0 | 2.5 | 3.0 |
|---|---|---|---|---|---|
| 번호 일치 | 73.00% | 87.33% | 84.67% | 87.67% | **89.33%** |

**87~89% 에서 정체합니다.** 3.0배면 모든 표본에서 `w_flat` 을 넘으므로(최대 비
1/0.404 = 2.48) 해상도 문제가 아닙니다 — 위에 적은 보간 변화 때문입니다.

### 그래서: 배율을 재시도 축으로 쓰세요

`architecture.md` 의 `_RETRIES` 가 이미 최대 3회입니다. 보간법 3종 대신
**배율**을 넣었을 때의 합집합입니다.

| 재시도 | 배율 | 번호 일치 |
|---|---|---|
| 1회 | `3.0` | 89.33% |
| 2회 | `1.5, 3.0` | 94.00% |
| **3회** | **`1.0, 1.5, 3.0`** | **95.00%** (low 95 / mid 93 / high 97) |
| 5회 | 전부 | 96.00% |

**이 배율 조합은 평가한 것과 같은 300장에서 고른 것이라 난이도가 약간 남아있습니다**
(후보 5개 중 3개 선택). 실제로는 95% 보다 조금 낮게 보세요. n=300 의 표준오차도
약 ±1.3%p 입니다. 배율을 확정하기 전에 **여러분의 구현으로 나머지 1,200장에서 다시
재세요.**

### 근본 해법은 계약 변경입니다 — 세 파트 합의 필요

재시도 3회로 95% 이고 정답 크기를 알면 100% 입니다. **남은 5%p 는 펴진 크기를
모른다는 것 하나에서 옵니다.** 2단계 모델이 `w_flat / w_obs` 비율을 출력 하나로 더
내면 없어지는 격차이고, 그러려면 `GeometryField` 에 필드가 하나 늘어야 합니다.
**계약 변경은 AI·SW 양쪽 합의 사항이므로(`CONTRIBUTING.md`) 여기서 정하지 않습니다.**
재시도 방식으로 먼저 돌리고, 필요해지면 제기하세요.

> 위 수치는 전부 **격자 축소 없는** 참조 구현으로 재습니다. 1/4 축소를 넣으면
> 조금 달라질 수 있습니다 — [5절](#5-격자-축소) 참고.

## 4. 골든 픽스처 — 구현이 맞는지 채점하는 법

평가 세트 1,500장(`low` / `mid` / `high` 각 500)에는 **정답 번호와 정답 제어점**이
같이 들어 있습니다.

```
data/eval/<bucket>/00000.png        관측 크롭 (흑백, 구겨진 것)
data/eval/<bucket>/00000.npz        dst_norm (48,2) · src_norm (48,2)
data/eval/<bucket>/manifest.jsonl   text(정답 번호) · w_flat · h_flat · 왜곡 파라미터 전부
```

**세 벌 전부 `target` 구간입니다** — 정의상 "보정 없이는 안 읽히고, 정답 제어점으로
펴면 읽히는" 샘플만 골라 구운 것입니다. **보정을 건너뛰면 0/1500 입니다.**

목표치는 [3절](#3-출력-캔버스-크기-out_shape--여기가-제일-중요합니다)의 `out_shape` 선택에 따라 다릅니다.

| 구현 | 기대치 |
|---|---|
| 정답 `(h_flat, w_flat)` 을 manifest 에서 읽어 넣으면 | **1500/1500** — 배관 배선을 동일하게 옮겼는지 보는 테스트 |
| 배율 재시도 `1.0, 1.5, 3.0` (실전 경로) | 약 95% — 3절 참고 |
| 크롭과 같은 크기 한 번 | 약 75% — 이 값이 나오면 `out_shape` 를 의심하세요 |

**먼저 첫 줄로 돌려 1500/1500 을 받으세요.** 그것이 TPS 방향·정규화·`BORDER_REPLICATE`
가 맞는지를 가리는 순수한 테스트입니다. 거기서 하나라도 틀리면 `out_shape` 를 아무리
잘 골라도 95% 가 안 나옵니다.

```python
import json, cv2, numpy as np
from wemeet.sw.rectify import apply_field          # 여러분이 만들 것

ok = 0
for bucket in ('low', 'mid', 'high'):
    for line in open(f'data/eval/{bucket}/manifest.jsonl', encoding='utf-8'):
        d = json.loads(line)
        obs = cv2.imread(f'data/eval/{bucket}/{d["file"]}', cv2.IMREAD_GRAYSCALE)
        z = np.load(f'data/eval/{bucket}/{d["npz"]}')
        fixed = ...          # apply_field 로 obs 를 z['dst_norm'], z['src_norm'] 으로 편다
        ok += (decode(fixed) == d['text'])
print(ok, '/ 1500')
```

**반드시 번호를 대조하세요. `decode(...) is not None` 으로 재면 안 됩니다.**
Code128 은 mod-103 체크디지트라 훼손된 판독이 약 1/103 로 체크섬을 통과해
**유효하지만 틀린 문자열**을 돌려줍니다. 실제로 이 데이터셋을 만들다가 1,500장 중
8장(0.53%)이 그렇게 새는 것을 발견해 라벨러를 고쳤습니다. 틀린 번호가 조용히 흐르는
것은 못 읽는 것보다 나쁩니다 — `docs/decisions/0003` 이 생성 모델 접근을 폐기한
이유와 같습니다.

> **데이터를 어디서 받나**: `data/eval/` 은 gitignore 입니다. Hugging Face
> `123metro/barcode-datasets` 의 `synthetic/v1/` 로 발행할 예정이고(작업 중),
> 그 전에는 AI파트에 요청하세요.

## 5. 격자 축소

`tps_flow` 를 전체 격자로 돌리면 예산을 크게 넘습니다. 1/4 격자로 계산하고
`cv2.resize` 로 늘리는 방식이 [stage2-handoff.md](stage2-handoff.md#격자-축소-14-은-선택이-아니라-필수입니다)
에 측정과 함께 있습니다. 확정 격자 `16×3`(48점)에서 **1/4 축소로 23.3 ms** 이고,
`architecture.md` 의 `warp` 예산 **24 ms** 안입니다.

**그 문서가 SW파트에 남긴 미측정 항목이 하나 있습니다.**

> 1/4 축소가 보정 품질을 떨어뜨리지 않는지는 아직 안 쟀습니다.

**이제 잴 수 있습니다.** 위 골든 픽스처를 축소 배율만 바꿔 두 번 돌리면 끝입니다.
전체 격자에서 N/1500, 1/4 축소에서 M/1500 을 비교하세요. 품질이 떨어지면
1/2(더 느림)이나 격자 `12×3`(36점, 18.4 ms)이 대안입니다.

## 6. 시간 측정 주의

**타이밍은 반드시 단독 실행으로 재세요.** 여러 프로세스를 병렬로 돌리면서 재면
같은 조건이 3.4 ms → 22.8 ms 로 **7배** 부풀려집니다. AI파트도 데이터 생성 중에
같은 현상을 겪었습니다 — 6샤드 병렬에서 코어당 처리량이 단독 실행의 40% 로 떨어졌고,
원인은 스레드 과다구독이 아니라 메모리 대역폭이었습니다(`tps_flow` 가 픽셀마다
`(h*w, n, 2)` 중간 배열을 만듭니다. M 버킷 크롭에서 약 200 MB).

축소를 넣으면 이 배열도 1/16 이 되므로 대역폭 문제도 같이 줄어듭니다.
