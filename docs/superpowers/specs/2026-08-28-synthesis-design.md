## 0. 요약과 범위

### 무엇을 만드나

Stage 2(기하 추정) 모델을 **여러 개 실험해 좋은 것을 고르기 위한** 학습·평가 데이터를
코드로 합성하는 방식이다. 산출물은 데이터가 아니라 **데이터를 만드는 규격**이다.

```
[1] 합성 방식 확정   ← 이 문서
[2] 스크립트 실행     학습 세트 + 평가 세트 생성
[3] 모델 비교         decisions/0003
```

### 왜 합성인가 — 선택이 아니라 유일한 길

Stage 1(검출)의 정답은 사람이 찍을 수 있다. 박스 네 점은 눈에 보인다.
그런데 **Stage 2의 정답은 "이 픽셀이 원래 어디 있었는가"라는 대응관계**이고,
구겨진 송장 사진을 보고 "이 막대가 펴졌을 때 x=137이었다"를 라벨링할 방법이 없다.

| 경로 | 정답 획득 | 판정 |
|---|---|---|
| 2D remap 합성 | 내가 넣은 변환의 역함수 | **즉시 가능, 무한** |
| 3D 렌더링 합성 | 메시의 UV 좌표 | 가능하나 셋업 비용 |
| 실촬영 | 없음 | **정답 불가** |

원본 재료도 실사 사진이 아니라 `python-barcode`로 **직접 렌더링**한다.
열화된 원본에 왜곡을 덧씌우면 "원래 이 막대가 어디 있었나"가 불분명해져
정답 제어점이 실제와 어긋난다.

### 안 만드는 것

| | 이유 |
|---|---|
| **접혀서 가려짐** | `GeometryField`가 `src`/`dst` 단일값 대응이라 **표현 자체가 불가능하다.** 접힘각이 90°를 넘어 표면이 스스로를 가리면 펴진 격자의 한 점에 대응하는 원본 위치가 여럿이거나 없다. 결함이 아니라 정직한 경계다 — 가려진 열은 정보가 없으니 실패로 보고하는 게 맞는 동작이다 |
| **원근(면외 기울기)** | `method="perspective"` 경로를 쓰려면 필요하다. v1 범위 밖. 목표 구간을 넓힐 수 있는 유일한 미사용 후보다 |
| **비닐/종이 높이장 분리** | "종이는 평탄한데 비닐만 구겨져 반사가 심한" 케이스를 만들 수 없다. 코드로는 `z` 를 하나 더 만드는 것뿐이라 v1.1 후보로 남긴다 |
| **모션 블러·주변 인쇄물** | v1.1 후보 |

### 이 문서가 뒤집는 것

| 대상 | 무엇을 |
|---|---|
| 설계 §4.1·§13 | `g = cumsum(m)` → `cumsum(1/m)` |
| 설계 §15-6 | "뒤집으면 디코딩이 실패한다" 폐기 |
| 설계 §9 성능 | 격자 축소가 "필요할 수 있다" → **필수** |
| `0004` 훼손 부여 | Albumentations `GridDistortion`/`ElasticTransform` 폐기 |
| `0003` 격자 | 4×3 → 6×3 권고 (근거의 한계도 함께) |

## 1. 구조

### 파일 분해

한 파일이 한 가지만 한다. 특히 **방향 함정이 사는 곳을 한 군데에 가둔다.**

```
wemeet/data/
  render.py      깨끗한 바코드 렌더링 (python-barcode 경계)
  surface.py     레시피 → 높이장 기울기 (z_x, z_y).  §3 수식의 집
  warp.py        기울기 → 매핑 → 관측 이미지 + 대응장 G      ← 방향 함정
  optics.py      Blinn-Phong 음영·정반사 (z_x, z_y 의 법선에서)
  augment.py     검출기 출력 모사 — 여백·회전(G 동반) / 블러·노이즈·JPEG
  synthesis.py   레시피 샘플링 + 조립 진입점
```

`warp.py`를 따로 떼는 이유가 크다. 이 프로젝트에서 가장 비싼 버그(설계 §8.5)가
정확히 여기 한 줄이었고, **약한 왜곡에서는 우연히 성공해서 안 잡힌다.**
한 파일에 가둬두면 §10의 검증 셋 하나로 전부를 지킬 수 있다.

`surface.py`는 왜곡 종류가 늘어도 인터페이스가 안 변한다 — 전부 기울기를 만드는 함수다.

### 산출물 — 이미지를 굽지 않고 레시피를 저장한다

수만 장을 파일로 구우면 수십 GB이고 8명이 각자 받아야 한다.
대신 **시드 + 파라미터 벡터(레시피)만 JSONL 로 저장**하고 필요할 때 재생성한다.

```jsonl
{"seed":4210,"symbology":"code128","text":"WEMEET0001","d_m0":2.0,"d_t":1.74,
 "preset":"crease","cyl_share":0.31,"components":[{"psi":12.4,"w_c":3.8,"offset":-0.12}],
 "light":[0.31,-0.18,1.0],"ks":0.62,"p":120.0,"sigma":0.4,"jpeg":86,"nx":6}
```

| | 실측 |
|---|---|
| 재현성 | 같은 레시피 두 번 → **SHA-256 비트 단위 동일** |
| 생성 속도 | 저해상도(315px) **71.7 장/초**, 784px **18.3 장/초** (1코어, 하한값) |
| 저장 용량 | 수만 줄이 몇 MB. git 에 들어간다 |

DataLoader 워커에서 즉석 생성이 가능하다. 워커 8개면 저해상도 500장/초 이상이다.

**단, 평가용 dev/test 세트는 이미지로 굽는다.** 코드가 바뀌어도 같은 사진으로 비교해야
성능 변화가 코드 탓인지 데이터 탓인지 갈린다.

### 의존 규칙과의 충돌 — 회피한다

`data`는 `schemas`와 `sw.decoding`만 부를 수 있는데, 라운드트립 검증은
`tps_flow`(= `sw.rectify`)를 필요로 한다. 규칙을 고치지 않고 넘어간다.

- 라운드트립 **테스트**는 `tests/` 에 둔다 — 규칙 밖이다
- 레시피에 구간 라벨을 붙이는 작업은 `scripts/label_recipes.py` 가 오프라인으로 한다

`wemeet/data/` 안의 코드는 `sw.rectify` 를 부르지 않는다.
**파일이 생기는 시점에 `uv run lint-imports` 로 실제로 막히는지 확인할 것** —
import-linter 는 존재하지 않는 모듈을 `forbidden_modules` 에 넣어도 조용히 통과시킨다.

### 실행 인터페이스

명령이 사람마다 달라지면 재현이 안 된다. 특히 **`0006`(디코더)이 정해져 ② 를 다시 돌릴 때
같은 명령이어야 한다.** 네 단계로 못 박는다.

```bash
# ① 레시피 뽑기 — 이미지는 안 만든다. 파라미터만 뽑으므로 즉시 끝난다
uv run python -m wemeet.data.synthesis make \
    --n 50000 --seed 42 --out data/recipes/train.jsonl

# ② 구간 라벨 붙이기 — 실제로 렌더·디코딩해서 판정한다 (여기서만 sw.rectify 를 쓴다)
uv run python scripts/label_recipes.py \
    data/recipes/train.jsonl --out data/recipes/train.labeled.jsonl

# ③ 평가 세트 — 목표 구간만 골라 이미지로 굽는다 (§7)
uv run python scripts/label_recipes.py \
    --extract-target --n 1000 --seed 7 --out data/eval/

# ④ 학습 — DataLoader 워커가 레시피를 읽어 즉석 생성한다
```

| 단계 | 예상 시간 |
|---|---|
| ① 5만 장 레시피 | 즉시 |
| ② 5만 장 라벨링 | 1코어 약 12분, 8코어 약 2분 |
| ③ 평가 1000장 | 1코어 약 17분 (6.3배 초과 생성 포함) |
| ④ 학습 중 생성 | 워커 8개에 500장/초 이상 |

② 가 렌더링과 디코딩을 두 번씩 하므로 가장 오래 걸린다.

**경로와 git 규약**

| | |
|---|---|
| `data/recipes/*.jsonl` | **커밋한다.** 몇 MB 이고 이것이 데이터의 정본이다 |
| `data/eval/` (구운 이미지) | `.gitignore`. 레시피에서 재생성된다 |
| 레시피 헤더 | 코드 커밋 해시를 기록한다 — 코드가 바뀌면 같은 레시피도 다른 이미지가 된다 |

### 소유권 (미결정)

`wemeet/data/synthesis.py` 가 문서상 데이터파트 소유인데 실제로 쓰는 것은 Stage 2 다.
**제안**: 위 6개 파일을 Stage 2(김대원·김강민) 소유로 옮기고,
데이터파트는 실촬영 수집·GT·평가 세트를 맡는다. 김강민이 양쪽에 걸쳐 자연스러운 접점이 된다.

## 2. 좌표 규약과 기하

### 규약 — 하나로 고정한다

| 기호 | 의미 |
|---|---|
| `x` | **관측** 가로 좌표 (사진에 찍힌 것). `z` 는 이 좌표 위의 높이 |
| `s` | **펴진** 가로 좌표 |
| `J = ds/dx = √(1+z_x²) ≥ 1` | 신장률 |
| `m = dx/ds = 1/J ≤ 1` | 압축률. 관측 모듈 폭 ≈ `d_m0 · m` (아래 주의) |

> **`관측 모듈 폭 = d_m0 · m` 은 관측 폭이 제대로 맞춰졌을 때만 성립한다.**
> 깨끗한 이미지 전체를 관측 폭에 매핑하므로, 펴진 총 길이가 원본 폭과 어긋나면
> 배율이 딸려 어긋나 모듈 폭이 의도한 값과 달라진다.
>
> **관측 폭을 맞추는 반복(`fit_obs_width`)과 기울기를 목표값으로 맞추는 것은
> 같은 함수 안에서 해야 한다.** 폭을 먼저 맞추고 나중에 기울기를 재조정하면
> 폭이 재조정 전 기울기에 맞춰져 있다. 스파이크에서 이 실수로 옥타브 실험이
> 두 번 무효가 됐다(전부 1차 디코딩 성공으로 나왔다).
> 성분이 하나뿐이면 영향이 작지만(목표 구간 15% vs 14%) 여러 개면 크다.

`m ≤ 1` 이 구조적으로 보장된다 — **종이는 늘어나지 않으므로** 정사영에서 항상 짧아 보인다.
`m` 을 손으로 쓰면 이 성질이 깨진다(설계 §4.2 원문의 물결 식이 `m > 1` 을 허용했다).
**항상 기울기에서 유도한다.**

### 매핑 — `cumsum(1/m)` 이다

```python
s = np.cumsum(1.0 / m, axis=1)      # 행마다 가로로만 적분
s_hat = (s - s[:, :1]) / (s[:, -1:] - s[:, :1])
```

`cumsum(m)` 이 아니다. `m ≤ 1` 이므로 `cumsum(m) < x` 가 되어
**펴진 폭이 관측 폭보다 좁아진다** — 물리적으로 불가능하다.

| | 원통 해석해 `r·arcsin((x−c)/r)` 대비 최대 오차 |
|---|---|
| `cumsum(1/m)` | **0.24 px** |
| `cumsum(m)` | **35.11 px** |

**이 오류는 디코딩으로 잡히지 않는다.** 잘못된 매핑으로 만들고 정답도 거기서 뽑으면
라운드트립이 자기일관적이라 읽힌다. "정답이 틀리는" 오류가 아니라
**"의도한 것과 다른 왜곡이 만들어지는"** 오류이고, 도메인 갭으로만 드러난다.

### `z` 는 만들지 않는다 — 기울기만 있으면 된다

| 필요한 것 | 유도 |
|---|---|
| 기하 | `m = 1/√(1+z_x²)` |
| 음영 법선 | `n ∝ (−z_x, −z_y, 1)` |

`z` 자체는 그림자나 시차에만 필요하고 우리는 쓰지 않는다.
접힘의 `ln cosh` 적분 같은 것을 계산할 필요가 없어지고, 성분 합성도 기울기끼리 더하면 된다.

> **주의**: `m` 과 `n_z` 는 다르다. `m = 1/√(1+z_x²)` 는 가로 압축만 재고
> `n_z = 1/√(1+z_x²+z_y²)` 는 양방향을 본다. 하나를 다른 하나로 대신 쓰면
> 능선이 누운 샘플에서 음영이 틀어진다.

### 관측 폭을 크롭으로 쓴다

종이를 감으면 정사영에서 좁아 보인다. 펴진 폭 `W` 가 관측에서 `2r·sinθ < W` 가 된다.

| | 판정 |
|---|---|
| 펴진 폭을 유지하고 양옆에 여백 | **안 된다** |
| 관측 폭을 그대로 크롭으로 | **이걸로** |

여백을 두면 모델이 **"여백이 넓으면 많이 휜 것"**이라는 가짜 단서를 배운다.
현장에서 검출기는 바코드에 딱 맞춰 자르니 그 단서가 없고, 그대로 무너진다.
`GeometryField` 의 정규화 기준이 애초에 크롭이라는 점과도 일관된다.

**실측 참고**: 784px 원본이 원통 70°에서 604px 가 된다.
디코딩 결과 자체는 두 방식이 같다(픽셀 값이 같고 여백만 다르다).

> **가정 (미검증)**: "여백을 가짜 단서로 배운다"는 모델을 학습시켜야 확인된다.
> 물리적으로 크롭이 맞다는 근거로 결정했다.

### `v = y` 근사

능선이 비스듬하면 세로 방향으로도 길이가 변해야 물리적으로 정확한데, 그걸 버리고
행마다 가로로만 적분한다. 근거는 설계 §8.1 실측 — **수직 변형은 디코딩에 무해**하다
(수직 사인파 진폭 32px 까지 전부 읽힘). 정답 제어점을 같은 규약으로 만들면
GT 는 자기일관적이다.

**행별 독립 정규화의 오차를 쟀다.**

| 케이스 | 행간 편차 | 최대 위치 오차 |
|---|---|---|
| 원통 / 접힘 ψ=0·30°·45° / 굽이치는 능선 | **0.00%** | 0.0 px |
| 구김 3옥타브 (방향이 여럿) | 5.44% | 17.0 px |

압축 프로파일이 `y` 를 따라 **평행이동만 하면** 각 행의 적분값이 같다 — 직선이든 굽은 능선이든.
방향이 다른 성분이 섞인 구김에서만 깨지고, 그 결과는 보정 이미지에서
막대가 세로로 물결치는 것으로 나타나 무해하다.

## 3. 왜곡 성분과 기울기 예산

### 성분은 셋이다

```
z_x(x,y) = 원통(x)  +  Σ_k  s_k · f'_k(t_k) · cos(ψ_k)
                              t_k = (x−c_x)·cos(ψ_k) + (y−c_y)·sin(ψ_k)
```

| 성분 | 기울기 | 최대 `|z_x|` | 현장에서 |
|---|---|---|---|
| **원통** | `−(x−c)/√(r²−(x−c)²)` | `tan θ` | 화물이 둥글어 라벨이 감긴 것 |
| **물결** (`sine`) | `s·cos(2πt/λ + φ)` | `2πA/λ` | 비닐 리플, 완만한 주름 |
| **접힘** (`crease`) | `s·tanh((t−t₀)/w_c)` | `tan α` | 송장이 한 번 접힌 자국 |

**구김은 별도 성분이 아니다.** `sine` 을 옥타브로 겹치면 나온다
(`λ_j = λ₀/2^j`, 기울기 가중 `p^j`). 왜곡 종류가 3개가 아니라 **2개**로 줄어든다.

`cos(ψ_k)` 가 붙는 이유: 능선이 누우면 가로 기울기가 그만큼 줄어든다.
진폭으로 파라미터화할 때는 `A = s_k·λ / (2π·cos ψ_k)` 로 역산한다.
**실측 검증**: ψ=0~60° 에서 `max|z_x| = 2πA·cosψ/λ` 오차 `1e-11`.

`tan α` 도 검증했다 — `w_c ≤ 80px` 에서 비율 정확히 1.000.
`w_c = 200px` 에서 0.961 로 떨어진다(`tanh` 가 폭 안에서 포화하지 못한다).
**분포 상한을 `w_c ≤ 20px` 로 두면 안전하다.**

### 기울기 예산 — 성분을 하나의 단위로 묶는다

판독 하한 `d_m0 · m_min ≥ c_min` 을 `m = 1/√(1+z_x²)` 에 대입하면

```
|z_x|_max  ≤  S_max = √( (d_m0 / c_min)² − 1 )
```

**모든 성분의 세기가 "최대 기울기" 하나로 표현되므로 예산을 선형으로 나눠 쓴다.**

> **`c_min` 과 `d_t` 는 역할이 다르다. 섞으면 안 된다.**
>
> | | 역할 |
> |---|---|
> | **`c_min`** | **넘으면 안 되는 하한.** `S_max` 를 정한다. 샘플마다 같다 |
> | **`d_t`** | **겨냥하는 목표 최소 모듈 폭.** 샘플마다 뽑는다 (§6). `d_t > c_min` |
>
> 샘플의 기울기는 `S_t = √((d_m0/d_t)² − 1)` 로 정확히 맞추고,
> `S_max` 는 그것이 하한을 넘지 않는지 보는 천장으로만 쓴다.

| `d_m0` | `S_max` (c_min=1.0) | 단독 원통이면 |
|---|---|---|
| 1.6 px | 1.25 | θ ≤ 51.3° |
| 2.0 px | 1.73 | θ ≤ 60.0° |
| 2.8 px | 2.62 | θ ≤ 69.1° |
| 5.5 px | 5.41 | θ ≤ 79.5° |

**물결 상한이 실측 경계와 정확히 일치한다.**

| `A/λ` | `m_min` | 최소 모듈 | 1차 | 보정 후 |
|---|---|---|---|---|
| 0.30 | 0.469 | 2.58 px | 실패 | **읽힘** |
| **0.41** | 0.362 | 1.99 px | 실패 | **실패** ← 유도한 상한 |

설계 §4.2 원문의 `Σ 2πA/λ ≤ 0.636` (= `A/λ ≤ 0.10`) 은 **4배 보수적**이었다.
실제로 `A/λ = 0.15` 는 잘 읽힌다.

### `c_min` 은 상수가 아니라 파라미터다 — v1 은 1.0

| 값 | 성격 |
|---|---|
| **1.0 px (v1 기본값)** | 합성 실측 한계에 맞춘 값 — **0.8px 까지 복원된다** |
| 2.0 px | 설계 §8.4 의 보수적 기준. 실촬영에서 노이즈가 크게 나오면 이걸로 |

설계 §8.4 는 "1~2px 이상 남아야 한다"고 썼는데 **실측 하한은 0.8px** 로
2배 이상 보수적이었다.

**v1 이 1.0 을 쓰는 이유는 안전보다 정합성이다.** `c_min = 2.0` 이면
`S_max = √((d_m0/2)² − 1)` 이 `d_m0 > 2.0` 에서만 정의되는데,
§6 의 분포는 목표 구간이 열리는 **저해상도(`d_m0` 1.6~2.8px)** 를 중심으로 뽑는다.
2.0 을 쓰면 그 구간의 절반이 표현 불가가 된다.

`c_min = 1.0` 이면 `d_t ~ U(1.3, 2.6)` 이 항상 `d_t > c_min` 을 만족해
`S_t ≤ S_max` 가 구조적으로 보장된다.

실촬영 베이스라인 후 `0005` 에서 확정한다.
0.8px 은 노이즈·블러·반사가 전혀 없는 조건의 낙관적 상한이므로,
실촬영에서 더 나쁘게 나오면 올린다.

### 초과분은 clip 하지 않고 스케일 다운한다

```python
scale = min(1.0, S_max / np.abs(z_x).max())
z_x *= scale;  z_y *= scale        # z 와 m 이 계속 일관됨
```

`np.clip(m, ...)` 은 안 된다. `m` 만 자르면 그에 대응하는 `z` 가 없어진다.
**실측: clip 은 화소 5.4% 에서 법선각이 최대 11.32° 어긋난다. 스케일 다운은 0.00°.**

그러면 음영·반사는 원래 곡률을 보여주는데 기하는 잘린 압축을 쓰게 되어,
**"반사 위치 ↔ 곡률" 상관이 clip 구간에서 물리적으로 틀어진다** —
높이장을 도입한 유일한 이유를 스스로 부수는 셈이다.

로그에는 `scale < 1` 이 된 비율을 남긴다. 높게 찍히면 분포 설계가 틀렸다는 신호다.

### 옥타브 감쇠 — persistence 0.7

| persistence | 목표 구간 | 불가 | 1차 성공 |
|---|---|---|---|
| 0.35 | 8% | 15% | 77% |
| 0.50 | 7% | 18% | 75% |
| **0.70** | **10%** | 18% | 72% |
| 1.00 (기울기 균등, 표준 fBm) | 5% | **25%** | 70% |

기울기 균등이 가장 어렵고 복원 불가로 많이 넘어간다.
**0.7 을 기본값으로 둔다** — 표준보다 약간 매끄럽게.
실제 구김 종이의 스펙트럼은 모르므로 파라미터로 남긴다.

## 4. 광학

법선은 이미 있다 — `n ∝ (−z_x, −z_y, 1)`. 기하에 쓴 바로 그 기울기다.

```
I = B(x,y) · (k_a + k_d · max(0, n̂·l̂))  +  k_s · (n̂·ĥ)^p
                                            ĥ = (l̂+v̂)/‖l̂+v̂‖,  v̂ = (0,0,1)
```

정사영 가정이다(§0의 원근 제외와 일관).

### 정반사는 곱이 아니라 더한다

| | 검은 막대 평균 밝기 | 0.6 이상으로 덮인 비율 |
|---|---|---|
| **더하기** (p=40) | **0.275** | **23.7%** |
| 곱하기 (p=40) | 0.005 | 0.0% |

**곱하면 검은 막대가 절대 지워지지 않는다** — `0 × 무엇 = 0` 이니까.
실제 비닐 반사는 막대를 하얗게 덮으므로 더하기가 물리적으로 맞고,
정보를 죽이는 메커니즘도 이것이다.

### 반사는 넓어야 정보를 죽인다

좁은 하이라이트(`p=200`)는 몇 열만 덮여 **디코더가 우회한다** — 1차·보정 후 모두 성공.
`p=40` 은 포화 20%로 둘 다 실패시킨다.

**`p ~ U(40, 300)`.** 시각적 사실성만 보면 `p` 를 크게 잡고 싶지만
그러면 정보를 죽이지 못한다. 실제 비닐 하이라이트가 얼마나 넓은지는 **현장 확인 항목**이다.

### 하이라이트가 곡률에 붙는다 — 마스크 방식과의 결정적 차이

| | 접힘 위치에서의 거리 |
|---|---|
| **Blinn-Phong** | **평균 0.7 px** (최대 1px) |
| 무작위 마스크 | 평균 86.8 px |

조명을 12방향으로 바꿔도 하이라이트 이동폭이 2px 다.

글레어를 타원 마스크로 얹으면 "어디에 반사가 생기는가"가 곡률과 무상관해진다.
실제로는 법선이 하프벡터를 향하는 곳에 정확히 생기고, **현장에서는 그 상관이 강한 단서**다.
같은 기울기를 쓰니 이 상관이 공짜로 물리적으로 일관된다. Blender 가 필요 없다.

### 광학은 `m` 이 잡지 못하는 방식으로 정보를 죽인다

하이라이트가 포화되면 그 열은 막대가 사라지는데 **`m` 히트맵에는 아무것도 안 나타난다.**
압축률 예산만으로는 판독 가능성을 보장할 수 없다.

§7 의 **사후 라벨링이 이걸 해결한다** — 구간 판정을 계산이 아니라 실제 디코딩으로 하니
예산이 커버 못 하는 소실 경로가 자동으로 반영된다.
로그에 포화 화소 비율을 남겨 목표 구간 비율이 무너질 때 원인을 갈라볼 수 있게 한다.

**실측 참고**: 구간별 평균 포화율이 목표 1.49% / 불가 4.35% / 1차 성공 1.83% 다.
포화율은 "불가"를 가리키는 신호로 쓸 수 있다.

## 5. 증강과 대응장 `G`

### 제어점 좌표를 직접 변환하는 코드를 두지 않는다

여백을 바꾸면 제어점을 **변환으로 얻을 수 없다.** `dst` 는 펴진 격자의 균등 4점
`u = 0, 1/3, 2/3, 1` 인데, 관측 크롭의 왼쪽 10%를 잘라내면 남은 크롭이 대응하는
펴진 범위가 `[0.13, 1]` 로 줄어든다. 새 `dst` 는 그 구간을 다시 정규화한 균등 4점이고
원래 좌표로는 `0.13, 0.42, 0.71, 1.0` — **원래 네 점 중 어느 것도 아니다.**

그래서 **밀집 대응장을 이미지와 나란히 들고 다니다가 맨 끝에서 한 번 샘플링한다.**

```
G[v, u] = (x_obs, y_obs)        펴진 정규화 좌표 (u,v) 의 내용이 있는 관측 픽셀 위치
```

**방향이 `G`(펴진→관측)여야 한다.** `F`(관측→펴진)로 들면 회전 시 벡터장을 리샘플해야 하고
제어점 추출이 2D 역문제가 된다. `G` 로 들면 **회전이 저장된 좌표에 아핀을 곱하는 것으로 끝난다.**

```
① 깨끗한 바코드                       render.py
② 기하 왜곡 → 관측 이미지 + G          warp.py     ← G 는 s_hat 의 행별 역보간
③ 음영·정반사                         optics.py
④ 기하 증강 (여백·회전) — 이미지와 G   augment.py
⑤ 제어점 = 최종 G 의 격자 샘플         warp.py
⑥ 광도 증강 (블러·노이즈·JPEG)         augment.py
```

**검증**: `G` 에서 뽑은 제어점이 직접 역보간한 결과와 **차이 0.000000** 으로 일치한다.

권장 `G` 해상도는 `33 × 513` (v × u). 크롭 크기와 무관하게 고정이고,
float64 두 장이라 270KB 다.

### 조립 순서 — 원칙은 맞지만 근거는 약하다

순서를 뒤집어 실측했다.

| 증강 | 순서를 바꾼 결과 |
|---|---|
| **크롭** | **차이 정확히 0.00e+00 — 완전히 교환 가능** (화소별 연산이니 당연) |
| 회전 | 평균 차이 0.017, 하이라이트 열 3px 어긋남 |
| 블러 | 평균 차이 0.0007, 정반사 피크 0.827 vs 0.908 |

**영향이 작다.** 순서를 물리적 인과에 맞추는 것은 원칙으로서 맞지만
성능 근거는 약하다 — 코드 가독성과, 나중에 그림자·시차 같은 **비화소별** 효과를
넣을 때를 위한 것으로 정당화한다.

### 두 종류를 시그니처로 가른다

```python
def geometric(img, G, rng) -> tuple[img, G]:   # 좌표를 반드시 함께 받는다
def photometric(img, rng) -> img               # 좌표를 건드리지 않는다
```

| | 무엇을 | 좌표 |
|---|---|---|
| `geometric` | 크롭 여백, 회전 잔차 ±5°, 리사이즈 왕복 | **G 를 함께 변환** |
| `photometric` | 초점 블러, 센서 노이즈, JPEG, 밝기·대비 | 안 건드림 |

### 여백은 −2% ~ +15%

| | u 범위 | 보정 후 |
|---|---|---|
| 패딩 +8% / +5% | [0.00, 1.00] | **읽힘** |
| 패딩 +15% / +15% | [0.00, 1.00] | **읽힘** |
| 잘라먹기 −2% / −2% | [0.02, 0.98] | **읽힘** |
| 잘라먹기 −6% / −4% | [0.06, 0.96] | **실패** |

**바코드 본체를 잘라먹으면 Code128 의 start/stop 이 사라져 어떤 제어점으로도 못 읽는다.**
음수 쪽을 −2% 로 제한한다. `u` 범위 재정규화는 정상 작동한다.

> 실제 검출기가 바코드를 잘라먹으면 그것은 **검출 실패**이므로 Stage 2 학습 데이터에
> 넣을 이유가 없다. 소량 넣어 confidence 를 낮추게 하는 것은 v1.1 후보다.

### 회전 잔차는 모델이 같이 펴게 둔다

`dst` 를 축정렬로 두고 `G` 만 회전시키면 모델이 회전까지 보정하는 답을 낸다.
이때 `src` 가 크롭 밖을 가리킬 수 있는데, 계약이 `−0.5 ≤ src ≤ 1.5` 로
여유를 둔 것이 바로 이 경우다.

## 6. 분포

### 지배 변수는 각도가 아니라 심볼 하나에 걸리는 픽셀 수다

Code128 은 심볼(11모듈) 안의 **상대 폭 비율**로 디코딩한다.
모듈이 5.5px 이면 심볼 하나가 60px 이라 어지간한 왜곡은 심볼 안에서 거의 균일해
비율이 안 깨진다. 2px 이면 심볼이 22px 이라 같은 왜곡이 비율을 무너뜨린다.

**그래서 `d_m0`(평탄 상태 모듈 폭)이 난이도의 손잡이다.**

| `d_m0` | 크롭 폭 | 목표 구간 | 불가 | 1차 성공 |
|---|---|---|---|---|
| **1.6~2.2 px** | 260~340 px | **12%** (열화 없으면 **18%**) | 40% | 48% |
| 2.0~2.8 px | 315~420 px | 8% | 10% | 82% |
| 2.8~4.0 px | 420~580 px | 7% | 18% | 75% |
| 전체 1.6~8.0 px | — | 6% | 33% | 61% |

**목표 구간은 좁은 띠 안에만 있다.** 그 위는 1차가 그냥 읽고, 그 아래는 복원 불가다.
다만 **띠의 절대 위치는 `d_m0` 에 따라 움직인다.**

| 측정 조건 | 목표 구간의 최소 모듈 폭 |
|---|---|
| `d_m0` = 5.5px (실험 08 격자) | 2.0 ~ 3.2 px |
| `d_m0` = 1.6~2.5px (실험 17 랜덤) | 평균 **1.57 px** |

절대 픽셀 값으로도, 압축률 `m` 으로도 일정하지 않다. 그래서 **띠를 수식으로 겨냥하지 않고
`d_t` 를 넓게 뽑은 뒤 §7 의 사후 라벨링으로 걸러낸다.** 이것이 목표 구간 비율을
생성 단계에서 70% 로 만들 수 없는 이유이기도 하다.

### v1 분포

```
d_m0    ~ U(1.6, 2.8) px          현장 확인 전까지 저해상도 중심
d_t     ~ U(1.3, 2.6) px          목표 최소 모듈 폭.  d_t < 0.97·d_m0
S_t       = √((d_m0/d_t)² − 1)    이 값을 정확히 맞춘다 (상한이 아니라 목표)

preset  : crease 45% / sine 30% / octave 15% / 원통 단독 10%
cyl_share ~ U(0.15, 0.45)         원통은 조연
K       : 1 → 70% / 2 → 30%

crease  : w_c ~ U(1, 9) px,  offset ~ U(−0.3, 0.3)·W
sine    : λ ~ U(0.5, 1.3)·W
octave  : 3옥타브, persistence 0.7, λ₀ ~ U(0.5, 1.0)·W
ψ       ~ U(−45°, +45°)           ← 근거 없음. 현장 확인 항목

light   : 방위 ~ U(−0.5, 0.5)², 고도 1.0
ks      ~ U(0, 0.9)
p       ~ U(40, 300)

sigma   ~ U(0, 0.8)               초점 블러. 열화는 약하게
noise   ~ U(1, 5)
jpeg    ~ U(70, 95)
```

**`S_t` 를 상한이 아니라 목표로 쓴다** — `ρ` 를 균등하게 뽑는 대신
목표 최소 모듈 폭 `d_t` 를 뽑고 기울기를 정확히 그 값에 맞춘다.
그래야 목표 구간 띠를 겨냥할 수 있다.

**열화는 약하게.** 실측에서 열화를 키우면 목표 구간이 18% → 12% 로 **줄었다.**
블러·노이즈는 `remap` 으로 복구되지 않으므로 "1차 성공"에서 "불가"로 건너뛴다.
열화의 역할은 목표 구간을 만드는 것이 아니라 **도메인 현실성**이다.

### 제어점 격자 — 6×3 권고, 근거의 한계도 함께

가로 제어점 개수가 **표현 가능한 최소 파장**을 정한다. 나이키스트 `λ ≥ 2W/(n_x−1)`.

| `n_x` | 예측 | 실측 |
|---|---|---|
| 4 (기본안) | 0.67 W | 0.50W 실패, 0.75W 성공 |
| 6 | 0.40 W | 0.35W 실패, 0.50W 성공 |

**세로는 늘리지 않는다.** 굽이치는 능선을 `λ_y` 0.5H~4H 로 흔들어도
`n_y = 2` 에서까지 전부 읽혔다. 설계 §7.1 이 세로를 "진짜 병목"으로 지목한 것은 틀렸다.

> **다만 근거가 약하다.** 랜덤 분포에서 목표 구간 비율이
> `n_x` = 4 / 6 / 8 에서 **14% / 12% / 15% — 차이가 없다**(N=120, ±3%p).
> 짧은 파장 샘플이 드물어서 6×3 의 이득이 안 드러난다.
> **후보 비교 실험에서 `n_x` 도 같이 흔들 것**이고, 현장에 짧은 파장 주름이
> 흔한지가 `0001` 확인 항목이다.

### 현장 확인 대기 항목

| 파라미터 | 지금 값 | 무엇을 확인 |
|---|---|---|
| `d_m0` | U(1.6, 2.8) | **바코드가 사진에서 가로 몇 px 인가** — 최우선 |
| `ψ` | U(−45°, 45°) | 주름이 막대와 어느 방향인가 |
| `λ`, `w_c` | 위 범위 | 주름이 얼마나 촘촘한가 |
| `p` | U(40, 300) | 비닐 하이라이트가 얼마나 넓은가 |
| `symbology` | code128 | `0001` |

**실패한 사진 10~20장을 받아 오면 앞의 네 개가 한 번에 해결된다.**

## 7. 학습 세트와 평가 세트 — 두 벌이다

### 구간 정의

| 구간 | 1차 디코딩 | 정답 제어점으로 보정 후 |
|---|---|---|
| **목표** | 실패 | **성공** ← Stage 2 가 값을 하는 유일한 구간 |
| 원리적 불가 | 실패 | 실패 |
| 1차 성공 | 성공 | — |

구간은 **계산하지 않고 실제로 디코딩해서** 라벨링한다(§4의 광학 소실 때문).
`scripts/label_recipes.py` 가 오프라인으로 한다.

### 두 세트의 목표가 반대다

| | 목적 | 목표 구간 비율 | 규모 |
|---|---|---|---|
| **학습** | 후보 모델들을 같은 조건에서 학습 | **맞추지 않는다.** 기하 분포 커버리지 | 수만 장 |
| **평가** | 후보 간 차이를 드러냄 | **100% 에 가깝게** | 수백~수천 장 |

**평가 세트가 목표 구간이어야 하는 이유**: 1차 성공 구간에서는 어떤 모델을 써도
결과가 같고(파이프라인이 Stage 2 를 부르지도 않는다), 원리적 불가 구간에서는
어떤 모델도 실패한다. 평가 세트에 1차 성공 샘플이 75% 섞이면
모델 A·B 의 성공률이 둘 다 80% 대로 나오고 **차이가 안 보인다.**

**학습 세트를 자르지 않는 이유**: 구간 경계는 디코더(`0006`)·심볼로지(`0001`)·
해상도에 따라 움직인다. 그 경계로 학습 데이터를 잘라두면 `0006` 이 정해질 때마다
데이터가 무효가 된다. 모델의 학습 타깃은 **제어점 정확도**이지 디코딩 성공이 아니다.
DocUNet·DewarpNet 도 "펴짐 정확도"로 학습하지 OCR 성공으로 자르지 않는다.

> **가정 (미검증)**: 커버리지 학습이 목표 구간 집중 학습보다 나은지는
> 모델을 학습시켜야 안다. 후보 비교 실험에서 **학습 세트 구성도 한 축으로 흔들 것**을 권한다.

목표 구간 200장을 실제로 채워 봤다.

|---|---|

## 8. 모델 입력 규격 — 비교를 위한 고정

**여러 모델을 같은 조건에서 비교하려면 입력 규격이 고정돼야 한다.**
아직 정한 것이 없어서 여기서 제안하고 미결로 표시한다.

### 제안: letterbox 대신 종횡비를 깬다

바코드 크롭은 가로로 길다(예 330×220). 고정 크기에 맞추는 방법이 둘이다.

| | 문제 |
|---|---|
| letterbox 패딩 | 모델이 내는 좌표가 "패딩된 이미지" 기준이 되어 환산이 필요하다 |
| **종횡비를 깨고 늘림** | **세로 변형은 무해하다**(설계 §8.1). 환산이 필요 없다 |

**세로 변형이 디코딩에 무해하다는 성질이 여기서 또 값을 한다.**
그리고 정규화 좌표는 리사이즈에 불변임을 실측했다.

| 입력 폭 | 판독 | 원본 기준 평균차 |
|---|---|---|
| 192 px | 성공 | 17.02 |
| 256 px | 성공 | 10.34 |
| 384 px | 성공 | 5.31 |
| 512 px | 성공 | 5.81 |

목표 구간 샘플(최소 모듈 1.98px, 관측폭 330px)을 네 크기로 리사이즈하고
**같은 정규화 제어점**으로 보정해 전부 판독됐다. 평균차는 리샘플 손실이다.

### 제안 규격 (미결정)

| 항목 | 제안 | 근거 / 미결 사유 |
|---|---|---|
| 크기 | **384 × 96** | 가로가 지배 변수다. 384px 이면 모듈 2px 크롭에서 정보 손실이 적다. 세로는 막대 방향이라 정보가 거의 없다 |
| 종횡비 | **깨고 늘림** (letterbox 안 함) | 위 |
| 채널 | 흑백 1채널 | 바코드는 명암만 쓴다. **다만 사전학습 모델 후보는 3채널을 기대하므로 복제 필요** |
| 정규화 | `/255` 후 0~1 | |
| 출력 | `src` 정규화 좌표 `n_x × 3 × 2` | `dst` 는 고정 격자라 예측하지 않는다 |

**미결정**: 정확한 크기(384×96 vs 512×128), 3채널 여부.
후보 모델이 정해지면 그 모델들이 공통으로 받을 수 있는 크기로 확정한다.

### 손실 함수의 좌표 단위 — 정규화 좌표를 그대로 쓰면 된다

화면에 찍힌 바코드가 크든 작든 **같은 기준으로 재려면** 어떻게 해야 하나.
크롭이 785px 일 때와 330px 일 때 "몇 px 틀렸다"는 같은 뜻이 아니다.

그런데 **정규화 좌표에서 L1 을 계산하면 이 문제가 저절로 해결된다.**

설계 §8.3 실측이 제어점 오차 **8px 까지 판독 성공**(모듈 5.5px)이었다.
즉 **모듈 폭의 1.45배**까지 허용된다. 그리고 크롭 폭과 모듈 폭은 비례한다 —
같은 심볼로지·자릿수면 모듈 개수가 고정이기 때문이다.

```
크롭 폭 = 165 × 모듈 폭          (Code128, 10자리, quiet zone 포함)

1.45 모듈 = 1.45 × 크롭폭/165 = 0.0088 × 크롭폭
```

| 크롭 폭 | 모듈 폭 | 허용 오차 | 정규화로는 |
|---|---|---|---|
| 785 px | 5.5 px | 8.0 px | 0.0088 |
| 330 px | 2.0 px | 2.9 px | **0.0088** |

**정규화 좌표 오차 0.0088 이 어떤 해상도에서든 1.45 모듈이다.**
해상도별 가중이 필요 없다. 목표는 "크롭 폭의 1% 안에서 맞히기"이고 꽤 관대하다.

> **전제**: 모듈 개수가 고정이다. 심볼로지(`0001`)나 자릿수가 데이터셋 안에서 섞이면
> 이 관계가 깨진다. **한 데이터셋에서는 하나로 고정할 것.**
> 섞어야 한다면 손실을 모듈 폭으로 나눠 정규화한다.

### 정답과 비교하는 방법

```
학습 (손실)
    L1( 예측 src , 정답 src )              정규화 좌표에서 그대로

평가 (지표 셋)
    ① 제어점 오차    |예측 − 정답| × 크롭폭  → px 로 환산       합성에서만
    ② 보정 후 판독   예측 src → tps_flow → remap → 디코더      ★ 주지표
    ③ 추론 시간      150ms 이하
```

② 가 주지표다(`0003`). 제어점 오차가 줄어도 결국 안 읽히면 의미가 없다.
**실촬영에는 정답 제어점이 없어서 ① 은 합성에서만, ② 는 양쪽에서 잰다.**

### letterbox 함정의 위험도 — 계약 docstring보다 낮다

`schemas.py` 의 경고("패딩된 이미지 기준이 되어 위아래로 밀린 채 펴진다")를 실측했다.
바코드 크롭은 가로로 길어서 정사각형에 맞추면 **세로 패딩만** 생기고,
가로 좌표가 안 변하므로 **환산을 빼먹어도 판독됐다.**

| | 판독 |
|---|---|
| letterbox 후 환산해서 보정 | 성공 |
| letterbox 후 환산 없이 그대로 | **성공** (실패해야 정상인데) |

경고는 유지한다 — 가로 패딩이 생기는 경우(세로로 긴 크롭)는 여전히 위험하다.
다만 **그 케이스는 미검증**이고 바코드 크롭에서는 드물다.
§8 제안(종횡비를 깨고 늘림)을 쓰면 letterbox 자체를 안 하므로 이 함정이 사라진다.

## 9. confidence — v1 에서는 학습하지 않는다

### 정의는 명확하다

```
confidence GT = 정답 제어점으로 폈을 때 읽히는가
```

이러면 `pipeline.py` 의 근거 없던 `confidence < 0.3` 이
**"펴도 못 읽을 것 같으면 시도하지 마라"**는 뜻이 된다.

### 그런데 이진 라벨은 노이즈가 크다

파라미터를 ±1% 흔들었을 때 라벨 유지율을 쟀다.

| | 실측 |
|---|---|
| 라벨 유지 | **88.3%** (53/60) |
| 뒤집힌 7건의 내역 | 목표→1차성공 4, 1차성공→불가 1, 1차성공→목표 1, 목표→불가 1 |

**뒤집힌 7건 중 5건이 목표 구간에서 나갔다.** 목표 구간이 전체의 15%뿐이니
그 안에서의 안정성은 훨씬 낮다. 실험 08 의 비단조 경계와 일관된다 —
디코더 스캔라인 운이 경계를 흔든다.

그리고 최소 모듈 폭 하나로 목표 구간을 맞히면 정확도 84.3% 인데
**다수 클래스 기준선도 84.3%** 다. 단순 특징으로는 전혀 안 갈린다.
이것이 "복잡한 신호가 있다"인지 "노이즈다"인지는 위 안정성 결과로 보면 **후자에 가깝다.**

### 결정

**v1 에서는 `confidence` 를 학습하지 않는다.** 제어점만 회귀하고 상수를 반환한다.
`pipeline.py` 의 0.3 임계값과 설계의 `degraded` 경로는 미결로 남긴다.

**v2 후보 — 소프트 라벨**: 같은 레시피를 미세하게 흔들어 여러 번 평가하고
**성공 빈도**를 confidence GT 로 쓴다. 샘플당 비용이 5~10배지만 경계 노이즈가 평균화된다.
목표 구간이 15%뿐인 지금 상황에서 confidence 의 이득이 작아 v1 범위에서 뺀다.

**포화 화소 비율은 지금도 쓸 수 있다.** 구간별 평균이 목표 1.49% / 불가 4.35% /
1차 성공 1.83% 로, "불가"를 가리키는 보조 신호다. 레시피 라벨에 기록해 둔다.

## 10. 검증 기준

승격 시 `tests/` 에 넣는다. 설계 §15 를 대체·보강한다.

### 방향 — 디코딩으로는 잡히지 않는다

1. **해석해 대조** — 원통에서 `cumsum(1/m)` 이 `r·arcsin((x−c)/r)` 와 **0.5px 안에서 일치**
   *(실측: 정정판 0.24px / `cumsum(m)` 35.11px)*
2. **오류판이 실패** — `cumsum(m)` 으로 만들면 위 대조에서 실패한다
3. **단조성** — `src` 가 `dst` 의 단조 역함수다. `m > 0` 이면 구조적으로 보장되므로
   깨졌다면 역보간을 빼먹은 것이다

### 증강 — 펴진 이미지 픽셀 비교로 잡는다

4. **좌표 정합성** — 증강 후 `G` 에서 다시 뽑은 제어점으로 펴면 증강 전에 편 결과와 일치한다

| 회전 −25° | 26.69 | 109.37 | 4.1× | 미변환만 실패 |

**증강 검증에 디코딩을 쓰면 안 된다** — 회전 20°까지 좌표가 틀려도 읽힌다.

5. `photometric` 을 통과시켜도 제어점이 비트 단위로 동일하다

### 기하·광학 일관성

6. **`m` 과 기울기가 일치** — `√(1/m² − 1)` 이 음영에 쓴 `|z_x|` 와 같다.
   *(clip 을 쓰면 화소 5.4% 에서 법선각 11.32° 어긋난다 — 이 테스트가 그걸 잡는다)*
7. **`m ≤ 1`** — 어떤 파라미터에서도 `m > 1` 이 나오지 않는다
8. **하이라이트가 곡률에 붙는다** — 접힘 위치(`|dz_x/dx|` 최대점)에서 5px 안
   *(실측 0.7px. 무작위 마스크는 86.8px)*

### 재현성·분포

9. **레시피 재현성** — 같은 레시피 두 번 → 이미지 바이트가 동일 *(SHA-256 확인)*
10. **평가 세트 구간 비율** — 목표 구간이 95% 이상
11. **`tps_flow` 항등** — 항등 대응(src == dst)에서 항등 매핑 *(설계 §15-4 유지)*

### 계약

12. 잘못된 `GeometryField` 가 거부된다 — 제어점 3개, `method="restore"`, `confidence=1.5`
    *(기존 `tests/test_schemas.py` 22개가 이미 덮는다)*
13. `uv run lint-imports` 통과. **`wemeet/data/` 가 `wemeet.sw.rectify` 를 부르지 않는다**
    — 파일이 생긴 뒤 일부러 import 를 넣어 CI 가 막는지 확인할 것

## 11. SW 파트에 넘길 것

### 격자 축소는 선택이 아니라 필수다

`tps_flow` 실측 (1코어, 단독 실행):

| 크기 · `n_x` | 전체 격자 | 1/2 | **1/4** | 1/8 |
|---|---|---|---|---|
| 380×280, `n_x`=4 | **128 ms** | 17.6 | **3.4** | 1.0 |
| 380×280, `n_x`=6 | **151 ms** | 38.6 | **5.2** | 1.3 |
| 784×220, `n_x`=4 | **176 ms** | 41.4 | **7.7** | 1.5 |
| 784×220, `n_x`=6 | **246 ms** | 66.0 | **13.0** | 4.1 |

**전체 격자는 20ms 예산의 6~12배다.** 설계 §9 가 "실험에서 한 번에 수십 ms 수준"이라고
적고 축소를 조건부로 써둔 것을 **확정 사항으로 바꿔야 한다.**

```python
mx, my = tps_flow(src_px/4, dst_px/4, (h//4, w//4))
mx = cv2.resize(mx, (w, h), interpolation=cv2.INTER_LINEAR) * 4.0
my = cv2.resize(my, (w, h), interpolation=cv2.INTER_LINEAR) * 4.0
```

**1/4 축소로 전부 20ms 안에 넉넉히 든다.** `n_x` 를 6으로 늘려도 5.2~13.0ms 다.
제어점이 12~18개뿐인 저주파 필드라 축소로 잃는 정확도는 작을 것으로 보이지만
**측정하지 않았다** — SW 파트가 1/4 와 전체 격자의 보정 결과를 비교해 확인할 것.

> 측정 주의: 여러 프로세스를 병렬로 돌리면서 재면 값이 크게 부풀려진다
> (같은 조건이 22.8ms → 3.4ms 로 7배 차이 났다). **단독 실행으로 잴 것.**

### `confidence` 분기를 어떻게 할지 결정해야 한다

§9 에서 **v1 은 `confidence` 를 학습하지 않기로** 했다. 그러면 `pipeline.py` 의
`confidence < 0.3` 분기가 의미를 잃는다. 모델이 상수를 반환하기 때문이다.

| 선택지 | |
|---|---|
| 항상 보정을 시도한다 | 가장 단순하다. 보정이 20ms 이내면 손해가 작다 |
| 다른 신호를 쓴다 | **포화 화소 비율**이 후보다. 구간별 평균이 목표 1.49% / 불가 4.35% / 1차 성공 1.83% |
| 임계값을 남겨두고 상수를 1.0 으로 | 분기가 사실상 죽는다. 코드는 안 고쳐도 된다 |

`degraded` 경로(보정하지 못하고 원본 크롭으로 디코딩)도 같이 걸린다.
**SW 파트 결정 사항이다.**

### 제어점 격자가 4×3 → 6×3 으로 늘어난다

`GeometryField` 의 제어점 개수가 12 → 18 이 된다(§6). `schemas.py` 는 "최소 4개"만
요구하므로 **코드 변경은 없다.** `tps_flow` 의 선형 시스템이 `12³ → 18³` 으로 커지는데
1/4 축소를 쓰면 3.4ms → 5.2ms 라 예산에 여유가 있다.

권고의 근거에 한계가 있다는 점도 §6 에 적어뒀다 — 랜덤 분포에서는 `n_x` 4/6/8 이
목표 구간 비율에 차이를 안 만든다. **후보 비교 실험에서 `n_x` 를 축으로 흔들 것이다.**

### 설계 §15-6 이 폐기됐다 — 검증 기준을 바꿔야 한다

**"src/dst 를 뒤집으면 디코딩이 실패한다"는 성립하지 않는다.** 20°~70° 전부 뒤집어도
읽혔다. 대체 기준은 §10 에 있다 — 해석해 대조, 단조성, 펴진 이미지 픽셀 비교.

SW 파트가 `rectify.py` 테스트를 짤 때 §15-6 을 그대로 쓰면 **통과하지만 아무것도
검증하지 못한다.** §10-1·2·3·4 를 대신 쓸 것.

### 1단계(검출)에 요구할 것 — 여백을 잘라먹지 말 것

Stage 1 → Stage 2 계약(`DetectedBarcode`)은 안 바뀐다. **제어점은 Stage 2 가 내는 것이고
Stage 1 은 크롭·각도·신뢰도만 준다.** 다만 크롭 방식에 요구사항이 생겼다.

| 크롭 여백 | 정답 제어점으로 보정 후 |
|---|---|
| 패딩 +8% ~ +15% | **읽힘** |
| 딱 맞게 −2% | 읽힘 (경계) |
| −6% (바코드 본체를 자름) | **실패** |

Code128 의 start/stop 이 잘리면 어떤 제어점으로도 복원할 수 없다.
**여유를 두고 크게 자르는 쪽이 안전하다.** 주변 인쇄물이 들어오는 것은
`augment.py` 가 모사할 수 있으므로 문제가 작다.

**크롭 크기를 통일하지 말 것.** 정규화 좌표의 기준이 크롭 원본 크기이고,
모듈 폭이 지배 변수다(§6). 모델 입력용 리사이즈는 Stage 2 안에서 한다(§8).

**회전 잔차 ±5° 는 허용된다** — Stage 2 가 같이 편다(§5).

> **미결 참고**: 계약의 `PipelineResult.detected` 는 단수인데
> `DecodeResult.candidate_count` 는 복수를 전제한다. 송장 한 장에 바코드가 여러 개일 때
> (`0001` 현장 확인 항목) 어느 것을 처리할지가 정해져 있지 않다. SW·AI 공통 미결이다.

### 그 외

- 합성이 만든 `(이미지, GeometryField)` 쌍은 `rectify.py` 의 픽스처로 그대로 쓸 수 있다
- 디코더(`0006`)가 바뀌면 `scripts/label_recipes.py` 를 다시 돌려야 한다.
  이미지를 굽지 않으므로 스크립트 한 번이면 된다

### 미검증으로 남기는 것

| | 왜 |
|---|---|

### 이 문서의 숫자를 어디까지 믿을 수 있나

- **디코더는 `zxing-cpp` 하나**다. `0006` 이 다른 것으로 정해지면 경계가 움직인다
- **심볼로지는 Code128 가정**이다. `0001` 미결정
- **실촬영이 하나도 없다.** 노이즈·블러는 흉내다
- 구간 경계가 비단조다 (`w_c`=6·α=55° 는 불가인데 `w_c`=9·α=55° 는 목표).
  디코더 스캔라인 운이므로 경계 근처 숫자는 **±1칸 흔들린다**고 보는 게 맞다
- 목표 구간 비율은 N=120 측정이라 오차가 **±3%p** 다
