# 합성 v1 본 생성 — 물리 치수 반영과 HF 발행

> **이 문서는 [합성 설계](2026-08-28-synthesis-design.md)를 대체하지 않는다. 델타만 적는다.**
> 구간 정의·비중·광학·기울기 예산 같은 본체는 그 문서가 계속 정본이다.

**계기**: 2026-09-14, 현장 바코드의 물리 치수를 받았다 — **50×30 mm 또는 60×40 mm**.
이 숫자가 지금까지 검증 불가능했던 상수들을 처음으로 검증 가능하게 만들었고, 검증해 보니
**셋이 틀렸다.**

| | 무엇 | 종류 |
|---|---|---|
| §1.1 | 라벨 높이 `H_OBS = 220` | 상대여야 할 값이 절대(px)로 박힘 |
| §1.2 | 주름 폭 `w_c ~ U(1, 9)` | 같음 |
| §1.3 | 렌더러가 위아래에 붙이는 흰 여백 6.67% | 아무도 의도하지 않은 라이브러리 산물 |

**범위**: 상수 셋 수정 → 재파일럿 → 학습 30,000장 · 평가 1,500장 생성 → HF 발행.

## 1. 물리 치수와 어긋난 상수 셋

### 1.0 기준 환산

렌더러는 10자 페이로드에 **154 모듈**(콰이엇 존 20 포함)을 쓴다. 라벨 폭이 곧 이 154 모듈이다.

```
50 mm / 154 모듈 = 0.325 mm/module      ← 0001 의 "송장 표준 0.33 mm" 와 일치
60 mm / 154 모듈 = 0.390 mm/module
```

`0001` 의 카메라 표를 0.325 mm 로 다시 계산해도 같은 값이 나온다
(1920px/60cm → 1.04 px, 4K/30cm → 4.16 px). **버킷 범위 `d_m0` 1.6~6.0 px 은 그대로
유효하다.** 다시 잡지 않는다.

폭이 50 mm 냐 60 mm 냐는 `±20%` 로 남지만, 아래 수정은 **둘 다 "라벨 폭의 몇 %" 로
표현**하므로 이 모호성이 그대로 타고 넘어간다. 상대로 쓰는 것이 요점이다.

### 1.1 종횡비 — `H_OBS = 220` 을 버린다

#### 왜 틀렸나

구현 계획의 고정 상수표가 이 값의 근거를 이렇게 적었다.

| 관측 높이 `H_OBS` | **220 px** | 스파이크 전체가 이 값으로 측정됐다 |

**검증된 값이 아니라 이어받은 값이다.**

`h = 220` 고정은 물리적으로 **"라벨 높이가 `71.5 / d_m0` mm"** 라는 뜻이다. 폭은 항상
50 mm 인데 높이만 따라 흔들린다.

| `d_m0` | 합성한 라벨 | 실제 (바 영역) | 합성 종횡비 |
|---|---|---|---|
| 1.6 | 50 × **44.7** mm | 50 × 22 mm | 1.12 : 1 |
| 3.0 | 50 × 23.8 mm | 50 × 22 mm | 2.10 : 1 ✔ |
| 6.0 | 50 × **11.9** mm | 50 × 22 mm | 4.20 : 1 |

**높이가 3.75배 흔들린다.** 맞는 구간은 `d_m0 = 220·aspect/154`, 즉 **2.86 ~ 3.29 px 뿐**
이다. `L` 버킷은 정사각형에 가까운 것을, `H` 버킷은 50×30 mm 라벨이 아니라 가늘고 긴 띠를
학습시키고 있었다.

#### 어떻게 고치나

`h` 를 상수로 두지 않고 종횡비에서 유도한다.

```python
ASPECT_RANGE = (2.0, 2.3)          # 레시피 축. 아래 「가정」 참고

M      = module_count(recipe.text)              # 콰이엇 존 포함
w_flat = int(round(M * recipe.d_m0))
h_flat = int(round(w_flat / recipe.aspect))
clean  = render_clean(recipe.text, recipe.d_m0, h_flat)
```

`module_count` 는 **래스터화 없이** 구한다 — `python-barcode` 의 인코더가 모듈 문자열을
그대로 준다.

```python
# render.py — python-barcode 의존을 이 파일에 가둔다는 규칙 그대로
_QUIET_MODULES = 20        # 양쪽 10 모듈씩. render_clean 의 quiet_zone 과 같은 값

def module_count(text: str) -> int:
    return len(barcode.get("code128", text).build()[0]) + _QUIET_MODULES
```

`len(build()[0]) + 20` 이 `render_clean` 이 실제로 만드는 폭과 정확히 일치하는 것을
확인했다 (`WEMEET0000` → 134 + 20 = 154, 렌더 실측 154).

> **가정 (미검증)**: 라벨 전체 높이의 **73~75% 가 바 영역**이고 나머지가 숫자 표기다.
> 여기서 50×30 → 2.27, 60×40 → 2.00 이 나오고 `U(2.0, 2.3)` 이 둘을 덮는다.
> 우리는 `write_text: False` 로 바만 그리고 탐지기 크롭도 바 영역이므로 이 구분이 필요하다.
> **11월 실촬영에서 확인되면 그 구간만 골라 보면 되고 재생성은 필요 없다** — `aspect` 가
> 레시피에 저장되기 때문이다.

> **종횡비 제약은 「펴진」 라벨에 건다.** 관측 크롭은 `fit_obs_width` 가 감김만큼 좁히므로
> 더 정사각형에 가깝다 (감기면 좁아 보인다). 그게 물리적으로 맞다 — 검증 #2 는 `w_flat /
> h_flat` 을 재지 관측 크롭을 재지 않는다. 실측 `w_obs / w_flat` 중앙값은
> `L` 0.956 / `M` 0.882 / `H` 0.737 이고 최소 0.445 다.

> **`h_flat` 이 「막대 높이」를 뜻하려면 §1.3 의 여백 제거가 선행되어야 한다.**
> 안 그러면 여기 적은 2.0~2.3 이 막대 영역이 아니라 여백 포함 종횡비가 된다.

### 1.2 주름 폭 `w_c` 가 절대 픽셀이다

`_make_grad` 를 보면 셋 중 둘만 상대다.

```python
grad_sine (w, h, rest, recipe.lam_f * w, ...)          # 상대 ✔
grad_crease(w, h, rest, recipe.w_c, offset=recipe.offset * w, ...)
#                       ^^^^^^^^^^^ 절대 픽셀 ✘
```

`w_c ~ U(1.0, 9.0)` 는 접힌 능선의 tanh 전이 폭인데 **픽셀 단위**다. 물리로 환산하면:

| 버킷 | `w_c` 물리 환산 (50 mm 라벨) |
|---|---|
| `L` (d_m0 1.6) | 0.20 ~ 1.83 mm |
| `H` (d_m0 6.0) | **0.05 ~ 0.49 mm** |

**고해상도 버킷이 물리적으로 3.75배 날카로운 주름을 받는다.** 카메라를 가까이 댔다고
비닐 주름이 날카로워지지는 않는다. `H_OBS` 와 정확히 같은 종류의 버그다.

#### 어떻게 고치나

`lam_f`·`offset` 과 같은 형태로 맞춘다.

```python
w_c_f  ~ U(0.003, 0.029)        # 라벨 폭의 0.3 ~ 2.9 %
w_c_px = w_c_f * w
```

**범위는 `L` 버킷의 현재 픽셀 분포를 보존하도록 잡았다.** 스파이크가 1~9 px 을 튜닝한
조건이 315 px 폭(≈ `L`)이었으므로, 실제로 검증된 지점을 기준으로 삼는다.

| 버킷 | 평균 `w` | 새 `w_c` (px) | 이전 |
|---|---|---|---|
| `L` | 316 | 0.95 ~ 9.2 | 1 ~ 9 (거의 동일) |
| `M` | 477 | 1.4 ~ 13.8 | 1 ~ 9 |
| `H` | 747 | 2.2 ~ 21.7 | 1 ~ 9 |

물리로는 전 버킷 공통 **0.15 ~ 1.45 mm** 다.

> **부수 효과 가설**: 설계 §7 이 "가설이다, 결론이 아니다" 로 남긴 U자형 출현율
> (`H` 의 1차 성공률만 54% 로 유독 낮음)의 원인 후보다. `H` 만 면도날 주름을 받고 있었다.
> **재파일럿이 이 가설을 부수적으로 검증한다** — `H` 의 1차 성공률이 올라가면 맞은 것이다.

### 1.3 렌더러가 위아래에 흰 여백을 붙인다

`render_clean` 의 기본 렌더를 열어보면 **165행 중 막대는 143행(86.7%)** 이고 위아래로
**11행(6.67%)씩 흰 여백**이 붙어 있다. 텍스트가 바뀌어도 이 비율은 일정하다.

이게 셋을 동시에 망친다.

| | 문제 |
|---|---|
| **종횡비가 15% 어긋난다** | `h_flat = w/aspect` 로 두면 **막대 영역** 종횡비는 `aspect / 0.867` = **2.31 ~ 2.65** 가 된다. §1.1 이 "바 영역 2.0~2.3" 이라고 적은 것과 다르다 |
| **`sat_ratio` 가 부풀려진다** | 흰 여백은 `base = 255` 라 정반사에서 쉽게 포화한다. 실측 중앙값 `L` 0.0061 → 여백 제외 0.0041 (**49% 부풀림**), 95%tile 0.1984 → 0.1790 |
| **검출기 여백과 이중 계상** | `geometric_margin`(−2%~+15%)이 이미 "검출기 크롭이 여유롭게 잘린 것" 을 모사한다. 렌더러 여백은 통제되지 않는 중복이다 |

#### 어떻게 고치나

`render_clean` 이 **리사이즈 전에 base 를 막대 행으로 자른다.** 6.67% 라는 라이브러리
의존 상수를 코드에 박지 않고 이미지에서 직접 찾는다.

```python
rows = np.where(arr.min(axis=1) < 128)[0]
arr  = arr[rows.min():rows.max() + 1]           # 리사이즈는 이 다음
```

검증했다.

| 확인 | 결과 |
|---|---|
| 폭 불변 | 1232 → 1232, `M = 154.0` 정확히 유지 → **기존 렌더 테스트 전부 통과** |
| 리사이즈 후 모든 행이 동일한가 | **참** — 세로 업스케일이 비로소 진짜로 무해해진다 |
| 최좁은 검은 줄 | 2 px (요청 모듈 폭 2.0) ✔ |

> 자르기 전에는 `h=142` 와 `h=460` 의 열 프로파일이 최대 **55.5 계조** 어긋났다.
> 여백 비율이 리사이즈로 보존되면서 흰 행과 막대 행의 섞임이 달라졌기 때문이다.

### 1.4 규칙 — 표면 기하는 상대, 카메라·센서는 절대

§1.1 과 §1.2 가 같은 종류였으므로, 나머지 파라미터를 같은 잣대로 전수 점검했다.
(§1.3 은 종류가 다르다 — 우리가 고른 값이 아니라 라이브러리가 붙인 것이다.)

> **표면 기하(라벨에 붙어 있는 것)는 라벨 폭 상대여야 하고,
> 카메라·센서·디코더의 성질은 픽셀·계조 절대여야 한다.**

| 분류 | 파라미터 | 판정 |
|---|---|---|
| 표면 기하 | `lam_f · w`, `offset · w` | ✔ 상대 |
| 표면 기하 | `psi`, `cyl_share`, `persistence`, `octaves`, `psi_spread` | ✔ 무차원 |
| 표면 기하 | **`w_c`** | ✘ **절대였다** → §1.2 |
| 표면 기하 | **라벨 높이 `H_OBS`** | ✘ **절대였다** → §1.1 |
| 광학 | `light`, `ks`, `p`, `k_a`, `k_d` | ✔ 무차원 |
| 카메라·센서 | `sigma`(초점 블러 px), `noise`(계조), `jpeg` | ✔ **절대가 맞다** |
| 카메라 척도 | `d_m0`, `d_t` | ✔ px — 이게 mm↔px 환산 자체다 |
| 디코더 | `c_min = 1.0 px` | ✔ 절대가 맞다 — 판독 하한이다 |
| 검출기 크롭 | `margin`(%), `rot_deg` | ✔ 상대·무차원 |

**규칙이 틀린 둘을 정확히 잡고 나머지 열넷을 전부 통과시킨다.** `sigma` 를 "이것도 상대로
바꿔야 하나" 로 헷갈리기 쉬운데, 초점 블러는 렌즈의 점퍼짐함수라 이미지 평면의 px 가
맞다 — 라벨의 성질이 아니다. **새 파라미터를 추가할 때 이 표에 한 줄을 먼저 적는다.**

## 2. 레시피 인덱스가 바코드 폭을 바꾼다

`draw_recipe` 가 `text = f"WEMEET{index:04d}"` 를 쓰고 `index` 는 렌더 카운터다.
파일럿은 3,000 까지만 돌아 안 드러났는데, 본 생성은 버킷당 10만 렌더를 넘는다.

| index | text | `w_flat` (d_m0=2.0) |
|---|---|---|
| 0 | `WEMEET0000` | 308 px |
| 9,999 | `WEMEET9999` | 308 px |
| **10,000** | `WEMEET10000` | **352 px** |
| **107,999** | `WEMEET107999` | **330 px** |

10,000번째부터 텍스트가 길어져 **`w_flat` 이 `d_m0` 과 무관하게 따로 움직인다.**
(330 < 352 인 것은 Code128 이 짝수 자릿수 숫자열을 mode C 로 2자리씩 압축하기 때문이다.)
그러면 "버킷 = 해상도" 라는 전제가 중간부터 깨진다.

**고친다**: `text = f"WEMEET{index % 10000:04d}"`.

텍스트 10,000종이면 학습 다양성에 충분하고, `w_flat` 이 `d_m0` 에만 의존한다는 성질이
유지된다. 텍스트가 겹쳐도 왜곡 시드가 달라 샘플은 전부 다르다.

> 페이로드 길이를 흔드는 것(`0001` 이 지적한 "10자 vs 20자" 문제)은 **v1 범위 밖**이다.
> 길이를 흔들면 같은 `d_m0` 에서 `w_flat` 이 달라져 버킷 정의가 다시 흔들린다.
> 길이 축은 버킷 층화를 다시 설계한 뒤에 넣는다.

## 3. 평가 세트 — 버킷 정의가 코드에 없다

설계 §7 의 평가 3벌과 코드의 학습 버킷이 다르다.

| | `low` / `L` | `mid` / `M` | `high` / `H` |
|---|---|---|---|
| 설계 §7 평가 | 1.6 ~ 2.2 | 2.5 ~ 3.5 | 4.0 ~ 6.0 |
| 코드 `BUCKETS` (학습) | 1.6 ~ 2.5 | 2.5 ~ 3.7 | 3.7 ~ 6.0 |

`synthesis.py` 에 설계값 그대로 추가한다.

```python
EVAL_BUCKETS = {"low": (1.6, 2.2), "mid": (2.5, 3.5), "high": (4.0, 6.0)}
```

`label_recipes.py --bucket` 은 `BUCKETS | EVAL_BUCKETS` 를 받는다.
평가는 `--per-band 500/0/0` 으로 돌려 **목표 구간만** 채운다 (설계 §10-10 의 "95% 이상" 을
100% 로 만족).

### `--bake` 가 메타데이터를 안 굽는다

설계 §7 이 요구한 **"preset 과 열화 파라미터를 메타데이터로 같이 굽는다"** 가 빠져 있다.
지금은 PNG + NPZ(제어점)뿐이다. `manifest.jsonl` 을 추가한다 — 한 줄이 한 장이다.

```jsonl
{"file":"00000.png","npz":"00000.npz","text":"WEMEET0417","band":"target",
 "sat_ratio":0.031,"m_min":1.71,"seed":1337,"bucket":"low","d_m0":1.83,"d_t":1.52,
 "aspect":2.14,"preset":"crease","w_c_f":0.018,"ks":0.41,"p":118.0,"jpeg":88, ...}
```

**정답 번호(`text`)가 이 파일의 존재 이유다.** 없으면 디코딩률을 못 잰다.

### 평가 세트의 렌더 상한은 어떻게 정하나

재파일럿(§4)은 `L`·`M`·`H` 만 돈다. 평가 3벌은 각각 그 **부분집합**이므로 별도로 재지 않고
**포함하는 학습 버킷의 측정 출현율을 그대로 쓴다** (`low`←`L`, `mid`←`M`, `high`←`H`).

```
렌더 상한 = 500 / 측정_출현율 × 1.5
```

부분집합이라 실제 출현율은 다를 수 있다. **500장을 못 채우면 상한을 늘리지 말고 부족분을
기록한다** — 평가 세트는 3벌의 장수가 같아야 버킷 간 비교가 성립하므로, 한 벌이 모자라면
**세 벌 모두 그 장수에 맞춘다.**

## 4. 재파일럿 — 건너뛸 수 없다

§1.5 대로 파일럿 실측치가 전부 무효가 됐다. **출현율이 렌더 상한을 정하므로, 재파일럿
없이는 본 생성 규모를 정할 수 없다.**

```
버킷마다 렌더 상한 3,000, --per-band 9999/9999/9999
```

받아 적을 것은 2026-09-08 파일럿과 같다.

| 항목 | 쓰임 |
|---|---|
| `seen["target"] / rendered` | 버킷별 목표 출현율 → **렌더 상한** |
| `tau_suggestion` | 세 버킷 목표 표본을 합친 95 백분위수 → **`τ` 기본값**. 프로토타입 후보 **0.128** (표본 165장, 못 믿는다) |
| `seen["first_ok"] / rendered` | §1.2 의 U자형 가설 검증 (프로토타입에서 `H` 가 53.9 → 64.8% 로 올랐다) |
| 벽시계 시간 | 버킷별 렌더+라벨링 속도 → **샤드 배분** |

렌더 상한은 예전과 같은 방식으로 **필요 렌더의 1.5배**로 잡는다.

> **상한은 시간이 아니라 렌더 개수로 건다.** 시간으로 걸면 기기가 달라질 때 데이터가
> 달라져서 "같은 레시피 두 번 → SHA-256 동일" 이 깨진다 (설계 §7).

### 프로토타입 선측정 (n=1,000) — 예산이 감당 가능한지 먼저 확인했다

계획을 쓰기 전에 세 수정을 스크래치에 프로토타입으로 만들어 버킷당 1,000장 돌렸다.
**본 재파일럿을 대체하지 않는다** (목표 표본이 25~105장뿐이라 `τ` 는 특히 못 믿는다).
목적은 "예산이 터지는가" 하나였다.

| 버킷 | 목표 (이전→프로토) | 1차 성공 | 불가·기하 | 불가·포화 | 속도 |
|---|---|---|---|---|---|
| `L` | 6.93% → **3.50%** | 80.2 → 88.8% | 3.30% | 4.40% | 36.5 장/s |
| `M` | 2.83% → **2.50%** | 85.5 → 87.2% | 8.20% | 2.10% | 16.6 장/s |
| `H` | 7.23% → **10.50%** | 53.9 → **64.8%** | 23.00% | 1.70% | 3.4 장/s |

**세 수정이 샘플을 전반적으로 쉽게 만든다.** 1차 성공이 세 버킷 모두 올랐고, `L` 의 목표
출현율은 반토막 났다. 방향은 물리적으로 옳다 — 세로 능선 변동이 줄고(§8 실측 `L` −21%),
`M`·`H` 의 면도날 주름이 뭉툭해지고(§1.2), 포화하던 흰 여백이 빠졌다(§1.3).

> **§1.2 의 U자형 가설은 지지된다.** `H` 의 1차 성공률이 53.9% → 64.8% 로 올랐다.
> `H` 만 면도날 주름을 받고 있었다는 설명과 맞는다. 다만 `H` 는 여전히 세 버킷 중
> 1차 성공이 가장 낮다 — 주름 폭이 유일한 원인은 아니다.

이 값으로 계산한 규모다. **세 버킷 모두 목표 쿼터가 병목**이고 불가·1차성공은 남아돈다.

| 버킷 | 필요 렌더 | 렌더 상한 (1.5배) | 샤드 | 샤드당 (기대 / 상한) |
|---|---|---|---|---|
| `L` | 142,900 | **214,000** | **2** | 0.54h / 0.82h |
| `M` | 200,000 | **300,000** | **6** | 0.56h / 0.84h |
| `H` | 47,600 | **71,400** | **7** | 0.56h / 0.83h |
| 계 | 390,500 (8.3h) | 585,400 (12.5h) | **15** | **기대 34분 / 최악 50분** |

샤드를 버킷별 예상 시간에 비례해 2 / 6 / 7 로 나누면 샤드당 부하가 0.54~0.56h 로 고르다.
**대비책(버킷당 1시간)에 걸리지 않는다** — 출현율이 나빠졌지만 예산은 버틴다.

상한까지 갔을 때의 불가·기하 수확량도 확인했다: `L` 7,062 / `M` 24,600 / `H` 16,422 로
쿼터 3,500 을 모두 넘는다.

### 출현율이 나쁘게 나왔을 때 (대비책)

**버킷당 벽시계 1시간(15샤드 기준)을 상한으로 둔다.** 렌더 상한 × 측정 속도가 이를 넘으면:

1. **`d_t` 범위를 낮춘다 (레버).** `d_t ~ U(1.3, min(2.6, 0.97·d_m0))` 은 목표 최소 모듈
   폭이고, 낮출수록 왜곡이 세져 목표 구간이 늘어난다. 하한은 `c_min = 1.0` 이다.
   **분포를 바꾸는 것이므로 설계 §6 을 고치고 재파일럿을 다시 돌려야 한다** — 프로토타입
   측정에서는 예산이 버텨서 쓰지 않았다
2. **목표 쿼터를 줄이고 부족분을 기록한다.** 설계 §7 의 "모자라면 채우지 말고 기록한다"
   와 같은 원칙이다 — 버킷마다 비중은 유지하고 절대 장수만 줄인다
3. 절대 하지 않을 것: **1차 성공으로 메우기**(그 버킷만 조용히 쉬워져 `eval/*` 가 오염된다),
   **시간으로 상한 걸기**(재현성이 깨진다)

세 버킷의 장수가 달라지면 학습 스크립트가 버킷별로 가중치를 줘야 하므로 `_stats` 에 남긴다.

## 5. 샤딩 — 16코어를 쓰되 재현성을 지킨다

`fill_bucket` 은 단일 프로세스라 버킷 3개 = 3코어가 상한이다. `--shard i/N` 을 추가한다.

| | 규칙 |
|---|---|
| 난수 | `np.random.default_rng([seed, i])` — 샤드마다 독립 스트림 |
| 렌더 상한 | `render_cap // N`, 나머지는 앞쪽 샤드에 하나씩 |
| 쿼터 | `per_band[b] // N`, 나머지는 앞쪽 샤드에 하나씩 |
| 인덱스 | `i * per_shard_cap + rendered` — 샤드 간 겹치지 않는다 |

**샤드 수 `N` 은 고정 상수로 못 박고 레시피 헤더에 기록한다.** `N` 이 바뀌면 같은 시드라도
다른 데이터가 나오기 때문이다. **`L` 2 / `M` 6 / `H` 7 = 총 15샤드** (§4 의 프로토타입
시간에 비례. 재파일럿이 크게 다르면 다시 나눈다), 16번째 코어는 OS 몫으로 남긴다.

`np.random.default_rng([seed, i])` 가 실제로 동작하는 것을 확인했다 — 샤드끼리 독립이고
같은 `(seed, i)` 는 같은 스트림을 준다.

`_stats` 병합은 `rendered`·`seen`·`kept` 합산, `hit_cap` 은 샤드별 OR, `shortfall` 재계산.
`tau_suggestion` 은 **병합된 JSONL 의 목표 구간 `sat_ratio` 에서 다시 계산**한다 —
샤드별 백분위수를 평균내면 틀린다.

> **샤드로 쪼개면 부족분이 단일 프로세스보다 커질 수 있다.** 한 샤드가 쿼터를 못 채운 채
> 자기 렌더 상한에 걸려도 다른 샤드의 남은 여유를 못 빌리기 때문이다. 같은 분포에서
> 같은 크기로 쪼개므로 차이는 작아야 하지만, **`_stats` 에 샤드별 `hit_cap` 을 남겨
> 부족분이 분포 탓인지 쪼갠 탓인지 갈릴 수 있게 한다.**

## 8. 열린 항목 — 정직하게 남긴다

### `n_y = 3` — 위험이 낮지 않다. 실측했다

제어점 격자 실험(`docs/experiments/2026-09-09-control-points`)은 `00_harvest` 부터
`05_grid` 까지 **전부 `H_OBS = 220`** 으로 돌았다. `n_x = 16` 은 영향 없다 (가로
나이키스트는 `w` 기준).

`n_y` 는 다르다. 능선 파장이 `lam_f · w` 로 **`w` 단위**이고 능선 축이 픽셀 공간이므로,
세로로 넘는 능선 주기 수가 **`h/w` 에 정비례**한다. 종횡비를 고정하면 이 값이 버킷 간에
통일되는데, `H` 는 `220/747 = 0.29` 에서 `1/2.15 = 0.465` 로 **늘어난다.**

`n_y` 가 잡아내야 하는 양(대응장 `G` 의 세로 변동, px)을 직접 쟀다 (버킷당 60 표본):

| 버킷 | `h=220` 중앙값 / 95% | `h=w/2.15` 중앙값 / 95% | 변화 |
|---|---|---|---|
| `L` | 3.36 / 11.99 | 2.66 / 10.44 | **−21%** |
| `M` | 9.75 / 29.56 | 9.66 / 29.38 | ±0% |
| `H` | 20.30 / 64.55 | **27.56 / 77.35** | **+36%** |

**이미 가장 어려웠던 `H` 에서 36% 더 어려워진다.** 크롭이 세로로 커져 px 단위 좌표 오차
`σ` 의 상대 크기가 줄어드는(h 220→347, +58%) 효과와 상쇄되는 수준이지, 쉬워지지 않는다.

### `G` 세로 해상도 `n_v = 33` 도 같이 재검증한다

`03_g_resolution.py` 를 열어보니 **`n_u` 만 흔들었다** (513/1025/2049/4097 → `g_remap_ok`
24/21/22/22, 차이 없음). **`n_v = 33` 은 한 번도 안 흔들렸다.** 세로 변동이 36% 늘었으므로
`n_y` 와 같은 이유로 재검증 대상이다.

### 그래도 후속으로 미룬다 — 되돌릴 수 있기 때문이다

제어점은 레시피에 저장되지 않고 `build()` 가 매번 계산한다. 따라서 `n_y`·`n_v` 가 바뀌어도

- **학습 세트는 재생성이 필요 없다** (레시피만 저장하므로)
- **평가 세트는 PNG 를 그대로 두고 NPZ 만 다시 구우면 된다** (이미지는 `n_x`·`n_y`·`n_v`
  에 의존하지 않는다)

재검증은 `00_harvest` + `02_ny` 를 **새 종횡비로** 다시 돌리면 된다 (`05_grid` 전수는
약 4시간이라 제외). 결과가 3을 뒤집으면 `0003` 의 16×3 확정을 갱신한다.

### 바 높이 비율 73~75% 가 미검증이다

§1.1 의 가정이다. 11월 실촬영에서 확인한다. `aspect` 가 레시피에 있으므로 확인 후
**재생성 없이 구간만 골라 보면 된다.**

### `w_c` 물리 범위 0.15~1.45 mm 도 미검증이다

§1.2 는 "`L` 버킷의 현재 픽셀 분포를 보존" 이라는 기준으로 범위를 잡았다. 실제 비닐 주름의
물리적 날카로움을 잰 데이터는 없다. 실촬영 `dev` 와 도메인 갭을 비교할 때 조정한다.

### 아카이브된 실험이 이 변경으로 재현 불가가 된다

`recipe_from_dict` 가 `aspect`·`w_c_f` 없는 옛 JSON 을 만나면 **`TypeError` 로 죽는다.**
조용히 기본값을 먹이지 않는다 — 옛 레시피를 새 파이프라인으로 재생성하면 다른 이미지가
나오므로, 조용한 성공이 조용한 오염이 된다. 해당 실험 README 에 "이 실험은 물리 치수 반영
이전" 이라고 명시한다.
