METRO · WE-Meet 2026 · 저장소 안내

내 파트만 알면 됩니다

난인식 바코드 복원 파이프라인 저장소를 처음 여는 사람을 위한 설명입니다. 외울 것은 네 개, 명령은 한 줄입니다.

01 / 우리가 없애려는 것

스캔 실패 한 건마다 사람이 공정을 거꾸로 걷습니다

인천세관 통합검사장에서는 컨베이어 위 화물의 바코드를 카메라로 읽습니다. 비닐에 빛이 반사되거나 송장이 구겨져 있으면 못 읽고, 그 화물은 노리드 존으로 빠집니다.

우리가 하지 않는 것. 바코드가 카메라를 향하게 놓는 일은 기존 설비가 합니다. 우리는 정면을 향하고 있는데도 구겨짐과 반사 때문에 안 읽히는 경우만 담당합니다.

02 / 만드는 것

사진 한 장이 번호가 되기까지 3단계

단계마다 담당 파트가 다릅니다. 그리고 전체가 0.5초 안에 끝나야 합니다 — 컨베이어가 멈추지 않으니까요.

03 / 시작하기

명령 한 줄이면 환경이 만들어집니다

uv를 먼저 설치하고, 그다음은 이 두 줄입니다.

git clone https://github.com/kim1034/2026-Wemeet-Barcode-Restoration.git
cd 2026-Wemeet-Barcode-Restoration
uv sync

파이썬 버전(3.12)까지 알아서 맞춰줍니다. activate 같은 건 필요 없습니다. 파이썬을 돌릴 때 앞에 uv run을 붙이면 됩니다.

uv run pytest                            # 테스트 11개가 통과하면 성공
uv run python -c "import wemeet; print('설치 완료')"

데이터 받기는 아직 없습니다. README에 uv run python -m wemeet.data.download가 적혀 있지만 그 파일은 아직 만들지 않았습니다. 받아올 데이터 자체가 없어서(수집은 9월) 지금은 uv sync까지만 하면 자기 파트 작업을 시작할 수 있습니다.

05 / 규칙 하나

데이터는 AI에서 SW로 흐르고, 부르는 건 SW가 AI를 부릅니다

가장 헷갈리는 지점이라 먼저 짚습니다. 두 방향이 반대입니다. "탐지가 먼저 실행되니까 AI가 위에 있어야 하지 않나?"가 자연스러운 의문인데, 의존 관계는 실행 순서가 아니라 누가 누구를 부르는가로 정해집니다.

이 방향을 어기면 순환이 생기고, 파이썬이 ImportError: cannot import name ... from partially initialized module을 냅니다. 이 오류는 실행 경로에 따라 나타났다 사라져서 원인 추적이 어렵고, 하필 통합하는 시점에 터집니다.

코드가 실제로 흐르는 순서

실선은 부르는 것, 점선은 결과가 돌아오는 것입니다. AI 코드는 불릴 때만 실행되고 스스로 아무것도 시작하지 않습니다.

아래 코드는 아직 만들지 않았습니다(SW파트가 만들 것). 계약에 따라 이런 형태가 됩니다.

# wemeet/sw/pipeline.py                          ← SW파트가 소유
from wemeet.ai.detection import detect         # ① 부르는 쪽에만 import 가 있다
from wemeet.ai.restoration import restore      #    AI 파일에는 이런 줄이 없어야 한다
from wemeet.sw.decoding import decode

def run(image_bgr):
    found = detect(image_bgr)                  # ② AI 코드가 여기서 실행된다

    if not found:                              # ③ 판단은 SW가 한다
        return 실패("not_detected")             #    AI 는 "찾은 것"만 돌려줬다
    best = max(found, key=lambda b: b.confidence)

    restored = restore(best)                   # ④ 하나만 넘긴다 — 고르는 건 ③에서 끝났다
    result   = decode(restored)                # ⑤ 재시도는 SW 몫

    result.candidate_count = len(found)        # ⑥ 몇 개 찾았는지는 decode() 가 모른다

    return PipelineResult(                     # ⑦ 중간 이미지를 버리지 않는다
        original_bgr_uint8=image_bgr,
        detected=best, restored=restored, decode=result,
    )
이 줄이 말해주는 것
①import가 SW 쪽에만 있습니다. AI 파일에 from wemeet.sw...가 생기면 순환이고 CI가 막습니다
②detect()가 먼저 실행되지만 부른 쪽은 run()입니다. 데이터는 AI→SW, 호출은 SW→AI
③"0개면?", "2개 이상이면?" 판단이 파이프라인에 모여 있습니다. AI로 새면 두 파트가 다르게 구현합니다
④restore()가 하나만 받는 이유입니다. 고르는 일은 ③에서 끝났습니다
⑤AI는 "한 번 복원"만 알고 재시도를 모릅니다
⑥총 개수는 decode()가 알 수 없는 정보라 파이프라인이 채웁니다
⑦중간 이미지를 버리면 화면에 "복원된 모습"을 못 보여줍니다

덕분에 AI파트는 자기 코드를 단독으로 돌릴 수 있습니다. detect(image) 한 줄이면 되고 서버도 디코더도 필요 없습니다. 만약 AI가 SW를 알고 있었다면 탐지 실험을 하려고 FastAPI까지 끌어와야 합니다.

외울 것은 세 줄입니다

  • AI파트는 자기 파일에 wemeet.sw나 wemeet.data라는 글자를 쓰지 않습니다. 공용이 필요하면 wemeet.schemas를 씁니다.
  • 데이터파트는 wemeet.sw.decoding까지만 쓸 수 있습니다. pipeline과 server는 안 됩니다.
  • 함수 안에서 import 하지 않습니다. 순환을 숨기는 응급처치일 뿐이고, 6개월 뒤에 왜 거기 있는지 알 수 없게 됩니다.
06 / 조심할 파일 하나

schemas.py는 두 파트가 주고받는 약속입니다

단계 사이로 흐르는 데이터의 형태를 여기서 고정합니다. 한쪽이 말없이 바꾸면 반대쪽이 전부 깨집니다.

실패했는데 이유가 없는 상태는 금지입니다. 판독에 실패했으면 failure_reason이 반드시 있어야 DecodeResult가 만들어집니다. 이유 없는 실패가 쌓이면 "어떤 훼손에서 왜 실패했나"를 분석할 수 없습니다.

그리고 파이프라인은 예외를 던지지 않습니다. 어떤 상황에서도 결과 객체를 반환합니다 — 현장 컨베이어에서 예외가 올라오면 서비스가 멈추고, 그게 곧 노리드 존 정체입니다.

07 / 작업 흐름

브랜치를 만들고, PR을 올립니다

git switch main
git pull                                 # 시작 전에 항상 최신으로
git switch -c ai/detection-baseline      # <파트>/<하는일>
# ... 작업 ...
uv run pytest                            # 올리기 전에 로컬에서 돌려봅니다
git push -u origin ai/detection-baseline

규칙이지만 강제하지는 않습니다. main에 직접 push가 되고, 승인이 없어도 머지 버튼이 눌리고, CI가 빨간 X여도 머지됩니다. 장치로 막지 않기로 했으니 사람이 지켜야 합니다.

빨간 X는 혼내는 게 아닙니다. 뭐가 잘못됐는지 12초 안에 알려주는 장치입니다. 없으면 2주 뒤에 남이 발견하고, 그때는 원인 추적이 어렵습니다.

검사가 실패했을 때

검사무엇을 보나이렇게 고칩니다
ruff 코드 스타일 uv run ruff format . 후 uv run ruff check --fix .
lint-imports 파트 간 import 규칙 부르면 안 되는 것을 불렀습니다. 필요해 보이면 설계가 잘못된 것이니 상의하세요
pytest 테스트 uv run pytest -x로 첫 실패만 보면서 고치는 게 빠릅니다

항목상태비고

CI 3검사있음PR마다 자동, 12초
Hugging Face 저장소있음데이터셋 2개 + 가중치 1개
1·2·3단계 실제 코드없음지금부터 만들 것
web/ 화면없음SW파트
데이터없음수집은 9월. 심볼로지 확정이 먼저입니다

Hugging Face 토큰 — 파일에 적는 게 아닙니다

데이터와 가중치는 저장소에 올리지 않고 Hugging Face에 둡니다. 토큰은 명령으로 등록합니다.

uv run hf auth login     # 토큰 붙여넣기. 화면에 안 보이는 게 정상입니다
uv run hf auth whoami    # 계정명이 나오면 성공

.env에 적어도 읽히지 않습니다 — 저장소에 .env를 읽는 코드가 없습니다. 옛 명령 huggingface-cli는 폐기됐으니 인터넷에서 본 명령은 hf로 바꿔 읽으세요.
